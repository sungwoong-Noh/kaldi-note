# 작업 흐름 — 스펙 → 계획 → 코드

이 프로젝트의 **모든 기능 개발은 세 단계를 순서대로 거친다.** 단계를 건너뛰지 않는다.

```
1. 스펙 (docs/specs/)      무엇을 · 왜 · 어떻게 동작해야 하는가
        ↓ 승인
2. 계획 (docs/plans/)      어떻게 개발할 것인가 (태스크 단위)
        ↓ 승인
3. 코드                     TDD로 구현
```

각 단계는 **사람의 승인**을 받고 다음으로 넘어간다. 스펙을 쓰면서 코드를 짜지 않고, 계획 없이 구현하지 않는다.

---

## 왜 이 순서인가

코드를 먼저 쓰면 "이게 맞게 동작하는가"의 기준이 코드 자신이 된다. 그러면 버그와 사양을 구분할 수 없다.

특히 이 프로젝트는 도메인이 숫자로 되어 있다. 추출 수율 18.0%가 이상 구간에 **포함되는지 아닌지**, C40 22클릭이 K-Plus 몇 클릭인지 — 이런 것들은 나중에 코드를 보고 "아마 이랬을 것"이라고 추정할 수 없다. **먼저 정하고 적어둬야 한다.**

---

## 1단계: 스펙

`docs/specs/YYYY-MM-DD-<기능명>.md` · 템플릿: [`docs/specs/TEMPLATE.md`](../specs/TEMPLATE.md)

### 스펙이 답해야 하는 세 가지

| | 내용 |
|---|---|
| **무엇을** | 이 기능이 하는 일. 범위와 **범위 밖**을 모두 적는다 |
| **왜** | 없으면 어떤 문제가 생기는가. 사용자 시나리오로 쓴다 |
| **어떻게 동작** | 인수 조건(Acceptance Criteria). **여기가 핵심이다** |

### ★ 인수 조건은 기계적으로 검증 가능해야 한다

이 규칙 하나가 나머지 전부보다 중요하다.

**모든 인수 조건은 자동화된 테스트로 옮길 수 있어야 한다.** 옮길 수 없다면 그건 인수 조건이 아니라 소망이다.

#### 형식

```markdown
#### AC-GRIND-01 · C40 22클릭은 660마이크론이다

- **Given** 클릭당 30µm, 영점 보정 0인 그라인더
- **When** 설정값 22로 마이크론을 계산하면
- **Then** 결과는 정확히 `660`이다
- **검증** 단위 테스트 `GrindConverterTest`
```

- **ID는 `AC-<기능>-<번호>`.** 유일해야 하고, 한 번 부여하면 바꾸지 않는다. 테스트가 이 ID로 스펙을 역참조한다.
- **값은 리터럴로 적는다.** "적절한 값", "대략 660 근처"가 아니라 `660`이다.
- **경계값은 따로 조건을 만든다.** "18~22%가 이상 구간"으로 끝내지 않고, `18.0`이 포함인지 `17.9`가 제외인지를 각각 조건으로 쓴다. 이 프로젝트에서 가장 자주 틀리는 부분이다.
- **에러도 조건이다.** 실패 시 어떤 HTTP 상태와 어떤 `code`가 나오는지 적는다.
- **검증 수단을 명시한다.** 단위 테스트 / 통합 테스트 / API 테스트 중 무엇인지.

#### 쓰면 안 되는 표현

아래 단어가 인수 조건에 들어 있으면 그 조건은 검증 불가능하다. 구체적인 값으로 바꾼다.

> 적절히 · 적당한 · 빠르게 · 충분히 · 유연하게 · 필요시 · 등등 · 기타 · 사용자 친화적 · 직관적 · 자연스럽게 · 잘 동작한다

```markdown
❌ 분쇄도 환산 결과를 적절히 반올림한다
✅ 대상 설정값은 소수 첫째 자리에서 HALF_UP으로 반올림한다. 900µm ÷ 22µm/click = 40.909... → `40.9`

❌ 잘못된 요청은 에러를 반환한다
✅ `micronsPerClick`이 null인 그라인더로 환산을 요청하면 HTTP `422`와 `code: "GRIND_NOT_CONVERTIBLE"`을 반환한다
```

#### 자동으로 검증할 수 없는 것

시각 디자인, 문구의 자연스러움 같은 것은 정직하게 **`## 수동 확인` 절에 따로** 적는다. 인수 조건에 섞지 않는다. 섞으면 "기계적 검증"이라는 기준 자체가 무너진다.

## 2단계: 계획

`docs/plans/YYYY-MM-DD-<기능명>.md` · 템플릿: [`docs/plans/TEMPLATE.md`](../plans/TEMPLATE.md)

- 스펙의 **모든 AC를 어느 태스크가 커버하는지** 표로 매핑한다. 빠진 AC가 있으면 계획이 미완성이다.
- 태스크는 TDD 사이클 단위로 쪼갠다: 실패 테스트 → 실패 확인 → 최소 구현 → 통과 확인 → 커밋.
- 각 태스크는 **테스트가 초록인 상태로 끝난다.**
- 코드 예시는 실제로 붙여넣을 수 있는 것을 쓴다. `TODO`, `// 구현 필요` 같은 자리표시자는 계획의 실패다.

---

## 3단계: 코드

- 계획의 태스크를 **순서대로** 실행한다.
- 테스트에 **AC ID를 반드시 남긴다.** 이게 스펙과 코드를 잇는 유일한 끈이다.

```java
@Test
@DisplayName("AC-GRIND-01 · C40 22클릭은 660마이크론이다")
void C40_22클릭은_660마이크론이다() {
    assertThat(converter.toMicron(C40, new BigDecimal("22"))).isEqualByComparingTo("660");
}
```

```ts
it('AC-GRIND-08 · 환산 결과에 추정치 배지가 표시된다', () => { /* ... */ });
```

- 메서드명은 기존 컨벤션대로 한국어를 쓴다. AC ID는 `@DisplayName` / `it()` 설명에 넣는다.
- 하나의 AC를 여러 테스트가 커버해도 되고, 하나의 테스트가 여러 AC를 커버해도 된다. **다만 모든 AC가 최소 한 번은 등장해야 한다.**

---

## 기계적 검증 — 커버리지 검사

AC ID가 테스트에 실제로 있는지 스크립트가 확인한다.

```bash
./scripts/check-spec-coverage.sh
```

- `docs/specs/`의 모든 스펙에서 `AC-XXX-NN` 형태의 ID를 추출한다
- 각 ID를 `backend/src/test/`와 `frontend/src/`에서 찾는다
- 하나라도 없으면 **실패(exit 1)** 하고 누락 목록을 출력한다

스펙의 `status`에 따라 검사 강도가 다르다:

| status | 검사 |
|---|---|
| `초안` | 건너뜀 |
| `승인` | 건너뜀 |
| `구현중` | 경고만 출력 (exit 0) |
| `구현완료` | **누락 시 실패** |

기능 구현을 끝내고 `status`를 `구현완료`로 바꾸는 순간부터 이 검사가 강제된다. CI에서도 돌아간다.

## 단계별 완료 기준

### 스펙 완료
- [ ] 무엇을 · 왜 · 어떻게 동작 세 절이 모두 채워져 있다
- [ ] 모든 AC에 유일한 ID가 있다
- [ ] 모든 AC의 값이 리터럴이다 (금지 표현 없음)
- [ ] 경계값이 각각 별도 AC로 있다
- [ ] 에러 케이스의 HTTP 상태와 `code`가 명시돼 있다
- [ ] 범위 밖(Non-goals)이 적혀 있다
- [ ] 사람이 승인했다

### 계획 완료
- [ ] 스펙의 모든 AC가 태스크에 매핑돼 있다
- [ ] 자리표시자(`TODO`, `TBD`, "나중에")가 없다
- [ ] 각 태스크가 독립적으로 테스트 가능하다
- [ ] 사람이 승인했다

### 코드 완료
- [ ] `cd backend && ./gradlew clean check` 통과 (해당 시)
- [ ] `cd frontend && pnpm typecheck && pnpm lint && pnpm test && pnpm build` 통과 (해당 시)
- [ ] `./scripts/check-spec-coverage.sh` 통과
- [ ] 스펙의 `status`를 `구현완료`로 변경
- [ ] **실제로 명령을 실행하고 출력을 확인했다.** 확인 없이 "완료"라고 말하지 않는다

## 예외

**버그 수정과 리팩터링은 스펙을 새로 쓰지 않는다.**

- 버그 수정: 기존 스펙의 AC를 위반한 것이므로, **깨진 AC를 재현하는 실패 테스트**를 먼저 쓴다. 스펙에 없던 동작이면 그건 버그가 아니라 새 기능이니 스펙부터 쓴다.
- 리팩터링: 동작이 안 바뀌므로 기존 테스트가 그대로 통과해야 한다. 테스트를 고쳐야 한다면 그건 리팩터링이 아니다.
- 오타·문서 수정·의존성 업데이트: 해당 없음.
