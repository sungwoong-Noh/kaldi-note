# 세션 핸드오버

작업은 **세션 단위로 나뉘고, 세션마다 다른 에이전트가 붙는다.** 새 에이전트는 이전 세션의 대화를 보지 못한다. 저장소에 남은 것만 볼 수 있다.

```
세션 시작:  /resume     → 상태 파악 + 테스트 실행 + 할 일 제안
세션 종료:  /handover   → 테스트 확인 + 체크박스 갱신 + JOURNAL 기록 + 커밋
```

---

## 무엇이 어디에 남는가

| 정보 | 저장 위치 | 이유 |
|---|---|---|
| **어디까지 했나** | `docs/plans/*.md`의 `- [ ]` 체크박스 | **단일 진실 원천.** 별도 진행표를 만들면 이중 관리가 되고 반드시 어긋난다 |
| **왜 그렇게 했나** | `docs/JOURNAL.md` | 체크박스가 못 담는 것 — 막힌 지점, 계획과 달라진 이유, 확인된 가정 |
| **무엇을 만들기로 했나** | `docs/specs/`, `docs/plans/` | 변하지 않는 계약 |
| **어떤 코드를 썼나** | git 히스토리 + PR | |

**핸드오버에서 실제로 깨지는 건 "어디까지"가 아니라 "왜"다.** 체크박스는 위치를 알려주지만, "Task 7에서 `MockRestServiceServer`가 안 돼서 다른 방식으로 갔다"는 남지 않는다. 그래서 JOURNAL이 있다.

---

## 브랜치와 PR

**태스크 1개 = 브랜치 1개 = PR 1개.**

```
feat/task-01-scaffolding
feat/task-02-grind
feat/task-03-extraction
...
```

- 브랜치명에 **계획 문서의 태스크 번호**를 넣는다. PR과 태스크가 1:1로 맞아 추적이 단순해진다.
- 태스크가 끝나면(모든 Step 체크 + 테스트 초록) PR을 만든다. PR 본문의 "관련"에 계획 문서와 태스크 번호를 적는다.
- **CI가 초록이어야 머지한다.** Squash and merge.
- 세션이 태스크 중간에 끝나도 **브랜치는 푸시해둔다.** 다음 세션이 이어받는다.

---

## 세션 시작 — `/resume`

새 세션은 **반드시 `/resume`으로 시작한다.** 커맨드가 하는 일:

1. `git status`, `git branch --show-current`, `git log --oneline -5` — 어디에 있나
2. `docs/JOURNAL.md`의 최근 항목 — 왜 그 상태인가
3. 계획 문서에서 **첫 미체크 태스크** — 무엇을 할 차례인가
4. **테스트 실행** — 지금 초록인가
5. 상태 요약 + 이번 세션에서 할 일 제안 → 승인 후 시작

### 4번이 핵심이다

**초록이라고 가정하고 시작하지 않는다.** 앞 세션이 깨진 상태로 끝났을 수 있고, 그걸 모르면 앞 세션의 실패를 내 작업 탓으로 오해하며 시간을 날린다.

빨간 상태로 시작하게 되면, **그 사실을 먼저 보고하고** 고칠지 이어서 진행할지 사람에게 확인받는다.

---

## 세션 종료 — `/handover`

작업을 멈추기 전에 **반드시 호출한다.** 커맨드가 하는 일:

1. **검증 실행** — `./gradlew clean check` + `./scripts/check-spec-coverage.sh`
2. **체크박스 갱신** — 실제로 끝낸 Step만 `- [x]`로. 안 한 것을 채우지 않는다
3. **JOURNAL 항목 추가**
4. **커밋 + 푸시**
5. 태스크가 끝났으면 **PR 생성**

### 태스크 중간에 끝날 때

흔한 일이고 문제없다. 다만:

- **태스크 전체 체크박스를 채우지 않는다.** 끝낸 Step만 체크한다
- JOURNAL에 **"Task N Step 3까지. 다음은 Step 4"** 를 명시한다
- 막혀서 멈춘 거라면 **무엇에 막혔는지, 무엇을 시도했는지**를 쓴다. 이게 없으면 다음 세션이 같은 벽에 다시 부딪힌다
- 브랜치를 푸시한다. PR은 만들지 않는다(태스크 미완이므로)

### 테스트가 빨간 채로 끝나야 할 때

가능하면 피하되, 불가피하면:

- **커밋 메시지 제목에 `WIP:`를 붙인다**
- JOURNAL에 **어떤 테스트가 왜 실패하는지** 정확히 쓴다
- PR을 만들지 않는다

## JOURNAL 작성 규칙

`docs/JOURNAL.md`는 **최신 항목이 위**로 오게 쓴다(역순). **append-only — 과거 항목을 고치지 않는다.**

```markdown
## 2026-08-15 · Task 2 — grind 순수 도메인

**브랜치:** `feat/task-02-grind` · **PR:** #3 (머지됨)
**상태:** 완료

### 한 일
- `GrindSpec`·`GrindConverter`·예외 2종 구현, 테스트 18개 통과

### 발견한 것
- Boot 4에서 `@ServiceConnection` 경로는 그대로였다 (계획의 가정 2번 해소)
- `BigDecimal.max()`가 스케일을 유지해서 `effectiveMinSetting()` 결과가
  `0.00`으로 나온다. `isEqualByComparingTo`를 써야 테스트가 통과한다

### 다음 세션에게
- Task 3부터. `extraction`은 `grind`와 독립이라 참고할 것 없음
- `ErrorCode`는 Task 5에서 만든다. Task 3에서 미리 만들지 말 것
```

### 쓸 것 / 쓰지 말 것

| 쓴다 | 쓰지 않는다 |
|---|---|
| 계획과 **달라진** 점과 그 이유 | 계획에 그대로 있는 내용 (중복) |
| 막힌 지점과 시도한 것 | "잘 진행됨" 같은 내용 없는 문장 |
| 확인·반증된 가정 | 코드 자체 (git이 기억한다) |
| 다음 세션이 모르면 헤맬 것 | 소감 |

**항목 하나가 15줄을 넘으면 대부분 계획 문서에 있어야 할 내용이다.** 계획을 고치고 JOURNAL에는 "계획 N절 수정함"만 남긴다.

## 계획과 실제가 어긋났을 때

구현하다 보면 계획이 틀렸다는 게 드러난다. 그때:

1. **계획 문서를 고친다.** 코드만 다르게 짜고 계획을 방치하지 않는다
2. JOURNAL에 **무엇을 왜 고쳤는지** 남긴다
3. 스펙(AC)까지 바꿔야 하는 거라면 **멈추고 사람에게 확인받는다.** AC는 승인된 계약이므로 에이전트가 임의로 바꾸지 않는다

문서와 코드가 어긋난 채로 세션을 넘기는 것이 이 프로젝트에서 가장 비싼 실수다. 다음 세션은 문서를 믿고 시작하기 때문이다.
