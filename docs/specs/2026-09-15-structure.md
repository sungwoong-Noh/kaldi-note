# 구조와 폼 스펙

> 작성 규칙은 [`docs/conventions/workflow.md`](../conventions/workflow.md) 참조.
> **모든 인수 조건은 자동화된 테스트로 옮길 수 있어야 한다.**

## 무엇을

폼의 오른쪽 가장자리를 하나로 맞추고, 푸어 스텝을 시간 축으로 그리고, **기록 화면이 「어떤
레시피로 어떻게 내렸는지」를 스스로 말하게** 만든다. 영어 상태값을 한글로 바꾸고 대표 수치
표현을 통일한다.

**백엔드를 한 줄도 건드리지 않는다.** enum도 API도 그대로이고, 한글화는 표시 계층에서만 한다.

시각 재설계 3부작의 **②구조와 ③폼을 합친 것**이다. ①(`2026-09-15-readability.md`)이 색과 크기를
잡았고, 이 스펙이 배치와 컨트롤을 잡는다.

### 범위 밖 (Non-goals)

- **백엔드 변경.** 0건이다. `StrengthZone`·`ExtractionZone`·`DegassingStatus` enum도, API 응답도
  그대로다. **이 스펙에 에러 인수 조건이 없는 이유다.**
- **커스텀 드롭다운 구현.** 네이티브 `select`를 유지한다. 이 프로젝트에는 shadcn/ui도 Radix도
  없어(2026-09-15 확인) 키보드 조작·포커스 트랩·ARIA를 전부 직접 만들어야 한다. 모바일에서
  OS 피커가 뜨는 이점도 잃는다.
- **누적 물량 막대.** 타임라인은 시간 축과 세로선까지다. 물이 차오르는 막대는 다음으로 넘긴다.
- **카드 제거.** 목록의 카드를 유지한다. `readability`가 `line`을 1.48→1.98:1로 올려 **테두리가
  실제로 보이게 된 지금은 카드가 제 역할을 한다.** 부엌에서 한 항목을 손가락으로 짚을 때
  경계가 있는 편이 낫다.
- **푸어 스텝 편집 행의 전폭화.** 한 줄을 유지한다. 전폭으로 펴면 스텝 하나가 4줄이 되어
  7스텝짜리 레시피 편집이 **7줄에서 28줄**로 늘어난다.
- **웹폰트 도입과 브랜드 갈색 변경.** `readability`와 같은 이유로 계속 범위 밖이다.

## 왜

### ① 폼의 오른쪽 끝이 제각각이다

실측값이다(360×800).

| 화면 | 컨트롤 | 오른쪽 끝 종류 |
|---|---|---|
| `/recipes/new` | 12개 | **10종류** — 112 · 176 · 192 · 195 · 207 · 228 · 237 · 246 · 279 · 344 |
| `/recipes/12/edit` | 36개 | **13종류** |
| `/brews/new` | 12개 | 4종류 |
| `/gear/grind-converter` | 3개 | 2종류 |

원인이 둘이다. **네이티브 `select`가 `option` 텍스트 길이에 맞춰 늘어나** 같은 폼 안에서 폭이
`44 · 102 · 108 · 191 · 204 · 212px`로 갈린다. 그리고 숫자 입력이 `w-20`(96px)으로 고정돼 또
다른 끝을 만든다. 사람이 「정돈되지 않았다」고 느끼는 1순위 원인이다.

### ② 기록 화면이 「어떻게 내렸는지」를 말하지 않는다

이 서비스의 존재 이유가 **「같은 레시피를 여러 번 내렸을 때 결과 차이를 추적하는 것」**이다
(`CLAUDE.md` 설계 결정 1). 그런데 기록 상세의 실측값이 이렇게 흐른다.

```
실측값
원두량 20.0g  물량 300.0g  물 온도 92°C
추출 시간 3:30  분쇄도 22
```

`flex-wrap`으로 흘러 값이 뭉치고, 라벨과 값이 같은 크기라 스캔이 안 된다. 그리고 **레시피
설계값과 대조할 수단이 화면에 없다** — 「레시피대로 내렸나」를 머릿속으로 계산해야 한다.

**추가 API 호출 없이 해결된다.** `useRecipeLabel`이 이미 `fetchRecipe`로 레시피 전체를
받아오면서 `title`과 `steps`만 꺼내 쓰고 `doseG`·`waterG`·`waterTempC`는 버리고 있다.

### ③ 화면에 영어가 그대로 나온다

`strengthZone`·`extractionZone`이 `IDEAL`·`UNDER`로, `sourceType`이 `CURATED`로 렌더된다.
**대문자 영어 배지는 AI 생성 페이지의 흔한 표시**이기도 하고, 브랜드 문서의 「외래어보다
우리말」과도 어긋난다.

### ④ 같은 개념을 화면마다 다르게 쓴다

레시피는 `30.0g → 500.0g`, 기록은 `1:15.0`이다. 둘 다 「비율」을 말하는데 형태가 다르다.

## 용어

| 용어 | 정의 |
|---|---|
| 일반 필드 | 폼의 컨트롤 중 **푸어 스텝 편집 행에 속하지 않는** `input`·`select`·`textarea` |
| 스텝 행 | `RecipeStepEditor`가 스텝 하나마다 그리는 한 줄. 타입 `select`와 숫자 `input` 2~3개 |

| 조용하다 | 값이 같을 때의 표시. 굵기·색을 더하지 않는다 |

스키마 변경 없음. **백엔드 변경 0건.**

## 바뀌는 것

### 폼 — 전폭 한 종류

일반 필드는 전부 `right = 344`(좌우 16px 패딩)다. 단위(`g`·`°C`·`초`)는 **입력칸 안쪽 오른쪽**에
넣는다. 지금은 칸 밖에 떠 있어 그 자체가 또 다른 끝을 만든다.

```
지금                                바뀜
원두량 [____] g                     원두량
물량   [______] g                   [_______________  g]
물 온도 [____] °C                    물량
       ↑ 끝이 다 다르다              [_______________  g]
                                                    ↑ 하나로 맞는다
```

**스텝 행은 예외다.** 한 줄을 유지하되 열 위치를 고정한다.

### 컨트롤 — 네이티브 유지, 모양만 교체

`select` 13개에 `appearance-none`을 주고 테두리·높이·화살표를 직접 그린다. 체크박스 1개도
같은 방식으로 **20×20px 모양**에 **44×44px 탭 영역**을 준다. 지금은 44px 규약 때문에 네이티브
사각형 자체가 44px로 커져 거대한 빈 상자로 보인다.

### 타임라인 — 읽기 2곳

```
지금                              바뀜
┌──────────────────────┐          0:00 ─┬─ 블룸    60g  15초
│ 0:00  블룸 60g 15초  │               │  중심에서 바깥으로...
│       중심에서...     │               │
├──────────────────────┤          0:15 ─┼─ 대기    30초
│ 0:15  대기 30초       │               │  45초까지 뜸을 들인다
└──────────────────────┘               │
  구분선뿐 — 시퀀스가              0:45 ─┴─ 푸어   240g  30초
  시퀀스로 안 보인다
```

**편집 화면에는 넣지 않는다.** 편집은 순서를 바꾸는 일이라 축이 방해가 된다.

### 기록 비교표

```
              레시피     실제
원두량        30.0g   ▸20.0g      ← 다를 때만 드러난다
물량         500.0g  ▸300.0g
물 온도       100°C    ▸92°C
추출 시간      3:30      3:30      ← 같으면 조용하다
```

위는 **실제 픽스처 값**이다(`hoffmann` 레시피 vs `brewLogWithTds`). 셋이 다르고 시간만 같다.

**한계를 숨기지 않는다.** 비교 대상은 **「지금의 레시피」**다. 레시피를 나중에 고치면 과거 기록의
비교가 새 값 기준이 된다. 기록 자체(`actual_*`)는 불변이라 조작되지 않지만, 「그때 설계값」은
어디에도 저장돼 있지 않다. **「현재 레시피와 비교」 문구를 붙인다** — 브랜드 문서의 「못 하는 것을
숨기지 않는다」다.

### 상태값 한글

| enum | 값 | 한글 |
|---|---|---|
| `StrengthZone` | `WEAK` · `IDEAL` · `STRONG` | 옅음 · 적정 · 진함 |
| `ExtractionZone` | `UNDER` · `IDEAL` · `OVER` | 부족 · 적정 · 과다 |
| `DegassingStatus` | `TOO_FRESH` · `IDEAL` · `PAST_PEAK` | 너무 신선함 · 적정 · 정점 지남 |
| `sourceType` | `CURATED` | 기본 제공 |

세 enum의 `IDEAL`이 모두 「적정」이다. 앞에 붙는 라벨(「농도」·「추출」·「가스」)이 맥락을 준다.

### 대표 수치 — 둘 다 `1:비율`

레시피 상세·카드도 `1:16.7` 형태로 바꾼다. 절대량(`30.0g → 500.0g`)은 바로 아래 메타줄에 남는다.
**비율은 배치 크기에 독립적이라 다른 레시피와 바로 비교된다.**

## 어떻게 동작 — 인수 조건

> 폼의 폭과 타임라인 위치는 **렌더 측정**으로만 판정한다. 클래스가 붙어 있어도 부모가 짓누르면
> 좌표가 달라진다 — `touch-targets`·`readability`가 같은 이유로 렌더를 쟀다.

### 폼과 컨트롤

#### AC-STRUCT-01 · 폼 4개의 일반 필드가 전부 같은 오른쪽 끝을 갖는다

- **Given** 360×800에서 `/recipes/new` · `/recipes/12/edit` · `/brews/new?recipeId=12` ·
  `/gear/grind-converter`를 연다

- **Then** 각 화면에서 **정확히 1종류**이고 그 값이 **344**다
- **검증** e2e `structure.spec.ts`

> 변경 전 종류 수는 `10 · 13 · 4 · 2`다. 이 조건이 그것을 1로 만든다.

#### AC-STRUCT-02 · `select` 13곳이 네이티브 모양을 벗는다

#### AC-STRUCT-21 · `select`에 화살표가 그려진다

- **Given** `/recipes/new`
- **When** 「공개 범위」 `select`의 `appearance`와 `backgroundImage`를 읽는다
- **Then** `appearance`가 `none`이고 `backgroundImage`가 **SVG를 담고 있다**
- **검증** e2e `structure.spec.ts`

> **추가 (2026-09-15).** `AC-STRUCT-02`는 `appearance-none`만 검사해서 **화살표가 사라진 것을
> 잡지 못했다.** OS 기본 모양을 벗기면 화살표도 함께 없어져 드롭다운인지 알 수 없게 된다.
>
> **Tailwind 임의값으로는 화살표를 그릴 수 없다.** `bg-[url('data:image/svg+xml;…')]`는
> data URI의 따옴표·괄호를 파서가 처리하지 못해 `background-image: none`이 된다(실측).
> `globals.css`의 `.select-chevron`에서 정의한다.

#### AC-STRUCT-03 · `select`의 렌더 높이가 44px를 유지한다

### 기록 비교표

#### AC-STRUCT-12 · 「현재 레시피와 비교」 문구가 있다

- **Given** `/brews/2`
- **When** 비교표 영역의 텍스트를 읽는다

> 화면이 모르는 것을 아는 척하게 된다.

#### AC-STRUCT-13 · 레시피를 못 읽으면 실측값만 보여준다

## 열어둔 결정

- **누적 물량 막대.** 타임라인에 물이 차오르는 표시를 더할지. **이번 타임라인이 실제로 도움이
  되는지 써본 뒤 정한다.**
- **「그때의 레시피」 저장.** 비교 대상이 현재 레시피라는 한계를 없애려면 `brew_logs`에 레시피
  스냅샷 컬럼이 필요하다. **백엔드 변경이라 이번 범위 밖이고, 비교표를 실제로 써보고 그 한계가
  문제가 될 때 정한다.**
- **목록 카드에도 「레시피와 달랐던 항목 N개」를 띄울지.** 카드마다 레시피를 받아와야 해 요청이
  늘어난다. 상세의 비교표를 써본 뒤 정한다.
