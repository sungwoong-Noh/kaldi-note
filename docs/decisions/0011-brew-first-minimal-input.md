# 0011. 기록 먼저, 입력은 최소로 — 기록 필수값은 원두량·물량뿐

## 맥락

1부 성공 기준은 「우리 둘이 실제로 매일 쓴다」(`0009-public-service-deferred.md`)인데, 두 사람
모두 쓰다가 손을 놓았다. 커피 한 잔을 기록하려면 레시피를 먼저 쓰고, 원두를 로스터 → 제품 →
재고 3단으로 등록하고, 그라인더를 등록해야 했다. `POST /brew-logs`가 `recipeId`·`beanBatchId`·
`userGrinderId`를 모두 요구했기 때문이다(`frontend/CLAUDE.md` 「로그를 남기려면 선행 데이터가
필요하다」). 기록이 「서류 작성」이 됐다.

흐름이 거꾸로였다.

- 예전: 어떤 레시피로 내릴까 → 레시피 작성 → 기록
- 실제 행동: 오늘은 이렇게 내려 보자 → 내린다 → 괜찮았다 → 다음에도 이렇게

디자인 요청과 시안: `docs/design/requests/2026-11-14-brew-first-design-request.md`,
`docs/design/kaldi-note-design/screens/10 Brew First.dc.html`.

## 결정

1. **기록이 입구다.** 홈은 「오늘」이고, 주 행동은 「기록하기」다. 레시피 없이 기록할 수 있다.
2. **기록의 필수값은 원두량(g)·물량(g) 둘뿐이다.** 내린 시각은 저장 시점으로 자동으로 채운다.
   레시피·원두·그라인더·분쇄도·물 온도는 전부 선택이다.
3. **레시피는 「괜찮았던 기록을 저장한 것」이다.** 레시피 작성 화면에서 시작하는 것이 아니라
   기록에서 「레시피로 저장」한다(P2). 레시피는 다음 잔의 출발점이다.
4. **「지난번과 같게」가 기본이다.** 직전 기록의 값을 미리 채우고, 같으면 바꾸지 않고 저장한다.

### 유지하는 것

- **ADR 0001(레시피와 기록 분리)은 그대로다.** 레시피는 「이렇게 내릴 것」, 기록은 「이렇게
  내렸다」다. 바뀌는 것은 둘을 만드는 **순서**이지 두 개념의 경계가 아니다.
- **ADR 0002(기록의 레시피 스냅샷)은 그대로다.** 기록이 레시피를 참조하면 지금처럼 스냅샷을
  박는다. 레시피 없이 쓴 기록은 스냅샷이 없을 뿐이다.

### 고른 이유

필수값을 「원두량·물량」으로 둔 것은 비율(물 ÷ 원두)이 핸드드립 기록에서 가장 작은 의미 단위이기
때문이다. 이것마저 선택으로 두면 기록이 「마셨다」 체크와 구분되지 않는다. 반대로 원두·그라인더를
필수로 남기면 등록 단계가 다시 입구를 막는다.

## 결과

- **가능해지는 것:** 지난번과 같으면 탭 3번으로 기록이 끝난다(P1 목표). 레시피·원두·장비가 하나도
  없는 첫날에도 기록할 수 있다.
- **바뀌어야 하는 것:** `BrewLogCreateRequest`의 `recipeId`·`beanBatchId`·`userGrinderId`·
  `actualGrindSettingValue`·`actualWaterTempC`를 선택으로 바꾼다. 원두를 이름만 직접 입력하는 경로가
  필요하다. 세부는 P1 스펙(`docs/specs/` 「빠른 기록」)이 정한다.
- **포기하는 것:** 모든 기록이 레시피·원두 재고에 묶여 있다는 가정. 레시피별 잔 통계는 레시피 없는
  기록을 빼고 계산한다.
- **뒤집으려면:** 2주 실사용(`docs/ROADMAP.md` 1부 목표 「커피를 내린 날의 80% 이상 기록」)에서
  필수값이 부족해 기록을 다시 볼 수 없었다는 불편이 나와야 한다. 그때도 입구를 막는 쪽보다
  「자세히」에 선택값을 늘리는 쪽을 먼저 검토한다.
