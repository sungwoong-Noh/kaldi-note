# 수동 확인

자동화된 테스트가 못 잡는 것을 사람이 확인하는 방법. **어떻게 확인하는가**가 이 문서의 주제다.
무엇을 인수 조건으로 쓰고 무엇을 수동 확인으로 미룰지는 [`workflow.md`](workflow.md)「자동으로 검증할 수 없는 것」이 정한다.

> **이 문서가 왜 있나.** 공개범위(FRIENDS)처럼 **두 계정이 있어야만 확인되는 동작**이 있는데, 카카오 OAuth는 자동화할 수 없고 테스트용 계정을 여러 개 만들 수도 없다. 그 우회 방법을 세션마다 처음부터 다시 만들었다 — **두 번 재발명한 뒤에 이 문서를 썼다**(`docs/JOURNAL.md` 2026-09-02).

---

## 두 계정이 필요한 확인

```bash
node scripts/open-as.mjs [userId]      # 기본 11
```

그 사용자로 **로그인된 브라우저 창**이 뜬다(390×844 모바일 뷰포트). 창을 닫으면 프로세스도 끝난다.

백엔드와 프론트가 떠 있어야 한다. 안 떠 있으면 스크립트가 그 사실과 띄우는 명령을 알려주고 멈춘다.

```bash
docker compose up -d
cd backend && SPRING_PROFILES_ACTIVE=local ./gradlew bootRun
cd frontend && pnpm dev
```

### 원리

accessToken은 메모리에만 살고, 앱은 세션이 없으면 `/api/auth/refresh`로 한 번 복구한다. 그래서 **refresh JWT를 직접 서명해 그 SHA-256 hex를 `refresh_tokens`에 넣고 쿠키로 심으면** 첫 화면에서 앱이 스스로 로그인 상태가 된다. 카카오도 DB 시드도 필요 없다.

### 알아둘 것

- **로컬 전용이다.** `application-local.yml`의 고정 시크릿으로 서명한다. 운영에서는 쓸 수 없고, 쓰려고 해서도 안 된다.
- **시크릿을 하드코딩하지 않는다.** 스크립트가 `application-local.yml`에서 읽는다. 값이 바뀌면 "로그인이 안 되는데 이유를 모르는" 상태가 되기 때문이다.
- **refresh 토큰은 1회용이다.** 백엔드가 갱신 시 회전시키므로 실행할 때마다 새로 발급한다. 창을 닫고 다시 열면 된다. `refresh_tokens`에 행이 쌓이는데 로컬이라 신경 쓰지 않는다.
- **스크립트는 `scripts/`에 있어야 한다.** 자기 위치에서 저장소 루트를 잡아 `frontend/node_modules`의 Playwright를 짚는다. 옮기면 깨진다.
- 없는 사용자 id를 주면 로그인이 안 되는 대신 **그 사실을 알려주고 멈춘다.**

### 확인용 계정 만들기

로컬에 계정이 하나뿐이면 상대가 없다. 두 번째 계정은 **한 번 카카오로 로그인해서** 만드는 것이 가장 정직하다(브라우저 프로필을 바꾸거나 지인에게 한 번 부탁한다). 그 뒤로는 `open-as.mjs`로 언제든 그 계정이 된다.

지금 있는 계정과 팔로우 관계는 이렇게 본다.

```bash
docker compose exec postgres psql -U kaldinote -d kaldinote \
  -c 'select id, nickname from users' -c 'select * from follows'
```

상호 팔로우가 없으면 `FRIENDS` 확인이 성립하지 않는다. 양쪽 행을 모두 넣어야 한다.

### 화면 흐름을 여러 개 밟아야 할 때

`open-as.mjs`는 **창을 하나 열어 주는 것**까지가 일이다. 확인할 항목이 여러 개면 창을 열고 손으로
누르는 대신, **같은 토큰 발급 로직을 재사용하는 Playwright 스크립트**를 임시로 짜는 편이 빠르다.
`open-as.mjs`의 서명·`refresh_tokens` 삽입 부분을 그대로 떼어 쓰고, 계정마다 컨텍스트를 따로 만들면
**두 계정을 한 스크립트 안에서 번갈아 볼 수 있다**(FRIENDS 확인이 이 방식으로 한 번에 끝난다).

**다만 스크립트가 초록이라고 상자를 켜지 않는다.** 단언은 내가 예상한 것만 본다 — 실제로 2026-09-05에
「보인다」를 `확인용 4:6`이라는 제목 문자열로 단언했다가 **틀렸다.** 로그는 보였는데 레시피 이름이
`비공개 레시피`로 마스킹돼 있었고, 그게 맞는 동작이었다. 그래서 각 단계에서 **스크린샷을 떠서 눈으로
본다.** 스크립트는 화면을 그 자리까지 데려다주는 수단이고, 판단은 캡처를 보고 한다.

스크립트는 저장소에 남기지 않는다. 재사용할 값어치가 생기면 그때 `scripts/`로 승격한다.

## 로컬에서 할 것과 운영에서 할 것

| 확인 대상 | 어디서 | 왜 |
|---|---|---|
| 공개범위(FRIENDS)·남의 화면 | **로컬** | 두 계정이 필요하고 반복해야 한다. `open-as.mjs`가 있는 이유 |
| 화면 흐름·계산값 | **로컬** | 데이터를 마음대로 만들 수 있다 |
| 폰 실물의 조작 감각 | **폰** | 젖은 손·한 손. 시뮬레이터는 이것을 대신하지 못한다 |
| 배포·도메인·인증서·실계정 로그인 | **운영** | 그 환경에서만 드러난다 |

**운영 DB에 확인용 데이터를 넣지 않는다.** 지울 수 있어도 넣지 않는다 — 운영은 확인 환경이 아니고, 접근 수단(SSH 키)도 GitHub Secrets에만 있다.

**운영 확인은 대부분 계정 하나로 된다.** 생성·편집·삭제, 로그아웃·재로그인이 그렇다. 두 계정이 필요한 것만 로컬로 돌린다.

## 확인한 뒤에 할 일

**체크박스는 실제로 눈으로 본 것만 켠다.** 이것이 이 문서에서 가장 중요한 규칙이다. 자동화된 테스트가 초록이라는 이유로 수동 확인을 켜면 그 항목은 영영 아무도 안 본다 — **테스트 279개가 초록인 채로 탭바가 화면 한가운데 떠 있던 적이 있다**(`docs/JOURNAL.md` 2026-09-02).

확인이 끝나면 그 스펙의 `## 수동 확인` 절에 **결과를 인용 블록으로 적는다.** 무엇을 봤는지가 남아야 다음 사람이 다시 밟지 않는다.

```markdown
- [x] 폰에서 탭 넷을 모두 눌러 이동되는지 본다

> **2026-09-02 확인.** 4/4 이동한다. 다만 탭바가 하단에 붙지 않는 결함을 찾아
> `AC-WEBSHELL-32`로 못박고 고쳤다.
```

**일부만 확인했으면 체크박스를 켜지 않는다.** 로컬에서는 됐고 폰에서는 못 봤다면, 인용 블록에 그렇게 적고 상자는 비워 둔다.

**결함을 찾으면 그 자리에서 고치지 않는다.** 스펙 → 계획 → 코드 순서는 수동 확인에서 나온 결함에도 그대로 적용된다(`workflow.md`). 인수 조건이 그 결함을 못 잡았다는 뜻이므로, 조건을 먼저 고쳐야 같은 것이 다시 새지 않는다.

### 수동 확인은 두 종류다 — 차단형과 비차단형

이 구분이 `status`를 정한다.

| | **차단형 `★`** | **비차단형** (기본) |
|---|---|---|
| 무엇 | 그 확인 없이는 **「이 기능이 동작한다」고 말할 수 없는 것** | 이미 자동으로 검증된 동작을 사람이 **감각으로 재확인**하는 것 |
| 왜 | 자동 테스트가 그 경로를 **전혀 밟지 못한다** | 자동 테스트가 같은 동작을 덮고 있다 |
| 예 | 가짜 구현으로 대체된 외부 서비스와의 실제 연동, 실계정 인증 | 폰에서의 조작감, 문구의 자연스러움, 레이아웃, 운영에서 한 번 더 눈으로 보기 |
| `status` | **막는다** | 막지 않는다 |

스펙에 쓸 때 **차단형만 `★`를 붙인다.** 표시가 없으면 비차단형이다.

```markdown
- [ ] ★ 실제 OCI 크리덴셜로 업로드 URL 발급 → PAR 업로드 → 공개 URL이 열리는지
- [ ] 폰에서 탭 넷을 눌러 이동되는지 (젖은 손·한 손 조작)
```

### 스펙의 `status`

**차단형이 하나라도 남아 있으면 `구현완료`로 올리지 않는다.** 비차단형만 남았으면 올린다.

`초안`인 스펙의 AC는 **커버리지 검사에서 통째로 건너뛴다.** 그래서 밀린 수동 확인은 문서 정리가 아니라
검증 구멍이다 — 다만 **어느 쪽 구멍인지가 다르다.**

- 차단형이 막고 있다 → 그 기능이 진짜로 되는지 아무도 모른다. **급하다.**
- 비차단형이 막고 있다 → 코드는 검증됐는데 **자동 검사까지 같이 멈춘 것뿐이다.** 손해만 있다.

> **이 구분을 만든 이유.** 원래 규약은 「수동 확인이 남으면 올리지 않는다」였는데, 2026-09-03에 세어보니
> **12개 스펙에서 지켜지지 않았고 지킨 3개 때문에 AC 96개가 검사에서 빠져 있었다.** 규약이 소수만
> 처벌하고 있었다. 남은 것이 전부 「폰에서 눌러보는 감각」인데 그것이 AC 96개의 자동 검사를 인질로 잡는
> 것은 이득이 없다(`docs/JOURNAL.md` 2026-09-03, 2026-09-05).

**비차단형만 남아 `구현완료`로 올릴 때는, 남은 항목이 몇 개이고 무엇인지 스펙의 인용 블록에 적는다.**
상자는 계속 비워 둔다. 사람이 폰으로 밟으면 그때 켠다. **올렸다고 없어진 것이 아니다.**

**이미 `구현완료`인데 차단형이 남아 있는 스펙**은 status를 되돌리지 않는다 — 검사를 줄이는 쪽이 더 나쁘다.
대신 **미검증이라는 사실이 보이도록** 그 항목 옆에 적어 둔다.
