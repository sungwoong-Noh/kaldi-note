# 세션 핸드오버

작업은 **세션 단위로 나뉘고, 세션마다 다른 에이전트가 붙는다.** 새 에이전트는 이전 세션의
대화를 보지 못한다. 저장소와 GitHub(이슈·PR)에 남은 것만 볼 수 있다.

```
세션 시작:  /resume     → 상태 파악(ROADMAP + 이슈) + 테스트 실행 + 할 일 제안
세션 종료:  /handover   → 검증 + 체크박스 갱신 + PR 본문 작성/갱신 + GOTCHAS + 이슈 닫기
```

작업 갈래(A/B/C)와 전체 흐름은 [`workflow.md`](workflow.md)가 정한다. 이 문서는 **세션을
어떻게 나누고 인계하는가**만 다룬다.

---

## 세션 종류와 흐름

| 세션 | 하는 일 · 산출물 | 브랜치 | 스펙 | 쓰는 스킬 |
|---|---|---|---|---|
| **설계 (A)** | `/interview` → 스펙 승인<br>`docs/specs/` | `docs/spec-<기능>` | **본문만** | `superpowers:brainstorming` |
| **구현 (A)** | 스펙의 「구현 순서」 태스크 실행 (TDD)<br>코드 + 테스트 | `feat/<기능>` | **체크박스만** | `superpowers:test-driven-development`<br>`superpowers:verification-before-completion`<br>`superpowers:systematic-debugging`<br>`/code-review`, `/simplify`<br>`/security-review` (인증 태스크 후) |
| **시각 보정 (B)** | 목업 대비 스크린샷 대조 → 수정 | `fix/<화면>` | 없음 — 이슈로 추적 | `mockup-checker` 서브에이전트 |
| **버그·잔손질 (C)** | 실패 테스트 → 수정 | `fix/<이름>` | 없음 (기존 스펙의 AC 위반) | `superpowers:systematic-debugging` |

**스펙의 「구현 순서」 체크박스는 구현 세션만 건드린다.** 설계 세션이 본문(시나리오·AC·계약)을,
구현 세션이 체크박스를 담당하면 같은 파일을 고쳐도 충돌이 거의 나지 않는다.

### 쓰지 말 것 — 이 프로젝트와 충돌하는 스킬

| 스킬 | 왜 안 되는가 |
|---|---|
| `superpowers:using-git-worktrees` | **항상** 격리 워크스페이스를 만든다. 순차 작업이면 불필요하고, 백엔드가 여러 워크스페이스로 갈라지면 5432 포트와 Testcontainers 재사용 컨테이너를 놓고 충돌한다 |
| `superpowers:executing-plans` | Step 1의 첫 항목이 위 스킬 호출이다. 게다가 이 프로젝트는 계획 문서를 폐지했다 — 스펙의 「구현 순서」를 직접 실행한다 |
| `superpowers:subagent-driven-development` | 태스크마다 서브에이전트를 띄운다. 이 프로젝트는 `/resume`·`/handover`로 세션을 나누는 쪽을 택했다. 둘을 섞으면 체크박스와 PR 본문을 누가 갱신하는지가 흐려진다 |

**병렬 작업의 worktree는 `EnterWorktree`로 직접 만든다.** 아래 "병렬 작업" 절 참조.

### 스킬을 새로 만들지 않는다

커피 도메인 규칙(반올림 스케일, SCA 상수, 단위 네이밍)을 프로젝트 전용 스킬로 뽑고 싶어질 수
있다. **하지 마라.** 그건 이미 `backend/CLAUDE.md`에 있고, 스킬로 또 만들면 두 곳이 어긋난다.

### 무엇부터 할지 정하는 법

```
만들려는 기능의 스펙이 이미 승인돼 있는가?

├─ 있다  →  구현 세션에서 바로 실행 (스펙의 「구현 순서」 태스크대로)
│
└─ 없다  →  설계 세션:  /interview → 스펙 승인
            구현 세션:  「구현 순서」 태스크 실행
```

### 인터뷰와 구현을 같은 세션에서 하지 않는 이유

컨텍스트 성격이 다르다. 인터뷰는 사람과의 대화로, 구현은 코드로 컨텍스트를 채운다. **한
세션에 둘 다 넣으면 정작 구현 중간에 컨텍스트가 찬다.** 설계 세션의 산출물은 스펙 문서라
핸드오버가 깨끗하므로 나누는 쪽이 항상 이득이다.

### 병렬 작업 — worktree

**같은 디렉터리에서 두 세션을 동시에 열지 않는다.** 한쪽이 `git switch`를 하면 다른 쪽 발밑에서
파일이 바뀐다.

동시에 작업하려면 **각 세션이 자기 worktree를 갖는다.**

```
세션 시작 시 EnterWorktree 호출 → .claude/worktrees/<이름>/ 에 격리된 작업 공간 생성
```

- **순차 작업**(한 번에 한 세션)이면 worktree가 필요 없다. 브랜치 전환으로 충분하다
- **동시 작업**이면 반드시 worktree를 만든다. 최대 2개까지 — `workflow.md`「멀티 에이전트」

### 병렬로 돌려도 되는 조합

| 조합 | 가능? | 이유 |
|---|---|---|
| 백엔드 1 + 프론트 1 + 디자인 1 | ✅ | 건드리는 파일도 포트도 다르다 |
| 디자인(B) + 아무거나 | ✅ | `docs/design/`만 고치고 서버를 띄우지 않는다 |
| **백엔드 2개** | ❌ | 아래 참조 |
| **프론트 2개** | ❌ | dev server 3000 포트 충돌 |

**백엔드 세션은 하나만 돌린다.** 이유가 둘이다:

1. `docker-compose.yml`의 PostgreSQL이 호스트 **5432 포트를 고정**으로 쓴다
2. `TestcontainersConfiguration`이 **`.withReuse(true)`** 라 컨테이너를 재사용한다. 두 세션이
   동시에 테스트를 돌리면 Flyway 마이그레이션과 테스트 데이터가 섞인다

### 언제 세션을 끝내는가

- 태스크를 완료했을 때
- **컨텍스트가 15~20% 남았을 때** — 가득 찬 뒤에 `/handover`를 부르면 늦다
- 막혀서 사람의 판단이 필요할 때 (이때는 브랜치를 푸시하고 draft PR이나 이슈에 막힌 지점을
  남긴다 — 아래 "PR 본문" 참조)

## 무엇이 어디에 남는가

| 정보 | 저장 위치 | 이유 |
|---|---|---|
| **어디까지 했나** | 스펙의 「구현 순서」`- [ ]` 체크박스 | **단일 진실 원천.** 별도 진행표를 만들면 이중 관리가 되고 반드시 어긋난다 |
| **왜 그렇게 했나** | PR 본문 「구현 중 결정」 | 그 세션이 끝나면서 함께 닫힌다 — 다음 세션은 머지된 PR을 보면 된다 |
| **반복되는 함정** | `docs/GOTCHAS.md` | 한 세션의 이야기가 아니라 **다음에 또 걸릴 만한 것**만 |
| **할 일** | GitHub Issue | 지금 하지 않지만 잊으면 안 되는 것 |
| **무엇을 만들기로 했나** | `docs/specs/`, `docs/decisions/`(ADR) | 변하지 않는 계약 |
| **어떤 코드를 썼나** | git 히스토리 + PR | |

**JOURNAL은 폐기됐다** (`docs/archive/JOURNAL.md`에 과거 기록만 남아 있다). 한 파일에 전
프로젝트의 "왜"를 계속 append하는 구조가 3,551줄까지 불어났고, 대부분은 해당 PR을 보면 알 수
있는 내용이었다. **PR 본문이 그 세션의 "왜"를 담고, GitHub Issue가 "할 일"을 담고,
`docs/GOTCHAS.md`가 "다음에도 또 걸릴 것"만 남긴다.**

## 브랜치와 PR

**세션 1개 = 브랜치 1개 = PR 1개.** 한 세션에서 태스크를 여러 개 진행해도 브랜치와 PR은
하나다.

```
feat/brew-log                 구현 세션 — 그 세션에서 한 태스크 전부
feat/recipe-crud
docs/spec-recipe              설계 세션 — 스펙 작성
fix/calendar-record-dot       버그 수정(C)
```

- 구현 브랜치명은 **기능 단위**로 짓는다. 태스크 경계는 **커밋 1개 = 태스크 1개**로 남기고,
  커밋 메시지에 무엇을 왜 했는지 적는다.
- **태스크마다 브랜치를 새로 만들어 스택하지 않는다.** 이유는 [`git.md`](git.md) 참조.
- 세션이 끝나면(진행한 태스크의 체크박스 전부 체크 + 테스트 초록) PR을 **하나** 만든다. PR
  본문의 "관련"에 스펙 문서와 이번에 끝낸 태스크를 전부 적는다.
- **설계 세션도 PR을 거친다.** 스펙은 이후 모든 구현의 근거이므로, 리뷰 없이 들어가면 안
  된다. PR 본문에 **무엇을 왜 결정했는지** 적는다.
- **CI가 초록이면 셀프 머지한다.** 리뷰어가 없는 1인(+에이전트) 개발이므로 예외를 두지 않는다
  — `git.md`「머지 규칙」.
- 세션이 태스크 중간에 끝나도 **브랜치는 푸시해둔다.** 다음 세션이 이어받는다.

> **예외 없음.** `main`에 직접 커밋하지 않는다.

## 세션 시작 — `/resume`

새 세션은 **반드시 `/resume`으로 시작한다.** 커맨드가 하는 일:

1. `git status`, `git branch --show-current`, `git log --oneline -5` — 어디에 있나
2. `docs/ROADMAP.md`의 진행 현황 + `gh issue list`(열린 이슈) — 왜 지금 이 상태인가
3. 스펙의 「구현 순서」에서 **첫 미체크 태스크**
4. **테스트 실행** — 지금 초록인가
5. 상태 요약 + 이번 세션에서 할 일 제안 → 승인 후 시작

**4번이 핵심이다.** 초록이라고 가정하고 시작하지 않는다. 앞 세션이 깨진 상태로 끝났을 수
있다.

## 세션 종료 — `/handover`

작업을 멈추기 전에 **반드시 호출한다.** 커맨드가 하는 일:

1. **검증 실행** — `./gradlew clean check` + `./scripts/check-spec-coverage.sh`
2. **체크박스 갱신** — 실제로 끝낸 태스크만 `- [x]`로
3. **PR 본문 작성/갱신** — 무엇을·왜·어떻게 확인했나·구현 중 결정·남은 것
4. **`docs/GOTCHAS.md` 갱신** — 다음에도 또 걸릴 만한 함정을 발견했으면 추가, 해결했으면 제거
5. **관련 이슈를 닫거나 갱신**
6. **커밋 + 푸시 + (태스크가 끝났으면) PR 생성**

### 태스크 중간에 끝날 때

흔한 일이고 문제없다. 다만:

- **태스크 전체 체크박스를 채우지 않는다.** 끝낸 것만 체크한다
- **막혀서 멈춘 거라면** draft PR을 열어(또는 기존 PR 본문에) 무엇에 막혔는지, 무엇을
  시도했는지 적는다. 이게 없으면 다음 세션이 같은 벽에 다시 부딪힌다
- 브랜치를 푸시한다

### 테스트가 빨간 채로 끝나야 할 때

가능하면 피하되, 불가피하면:

- **커밋 메시지 제목에 `WIP:`를 붙인다**
- PR을 만든다면 draft로 열고, 본문에 **어떤 테스트가 왜 실패하는지** 정확히 쓴다

## PR 본문 작성 규칙

`.github/pull_request_template.md`의 절을 채운다. 예전 JOURNAL이 하던 일 중 "왜 그렇게
했는가"는 여기로, "다음에도 걸릴 함정"은 `docs/GOTCHAS.md`로 나뉘었다.

| 절 | 쓴다 | 쓰지 않는다 |
|---|---|---|
| **왜** | 관련 스펙/ADR/이슈 링크. 스펙과 **달라진** 점과 이유 | 스펙에 이미 있는 내용의 반복 |
| **구현 중 결정** | 사람에게 묻지 않고 정한 것과 그 이유 (W8) | 되돌리기 어려운 결정 — 그건 먼저 물어야 한다 |
| **어떻게 확인했나** | 실제로 실행한 명령과 결과 | 체크만 하고 안 돌린 것 |
| **남은 것** | 이어받을 태스크, 열어야 할 이슈 | "잘 진행됨" 같은 내용 없는 문장 |

**PR 본문 하나가 너무 길어지면** 대부분 스펙에 있어야 할 내용이 섞인 것이다. 스펙을 고치고
PR 본문에는 "스펙 N절 수정함"만 남긴다.

## 스펙과 실제가 어긋났을 때

구현하다 보면 스펙(특히 「구현 순서」)이 틀렸다는 게 드러난다. 그때:

1. **스펙의 「구현 순서」를 고친다.** 코드만 다르게 짜고 문서를 방치하지 않는다
2. PR 본문의 「구현 중 결정」에 **무엇을 왜 고쳤는지** 남긴다
3. **AC까지 바꿔야 하는 거라면 멈추고 사람에게 확인받는다.** AC는 승인된 계약이므로 에이전트가
   임의로 바꾸지 않는다

문서와 코드가 어긋난 채로 세션을 넘기는 것이 이 프로젝트에서 가장 비싼 실수다. 다음 세션은
문서를 믿고 시작하기 때문이다.
