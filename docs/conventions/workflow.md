# 작업 흐름

이 문서가 **갈래·흐름·문서 수명·완료 정의의 유일한 원본**이다. `CLAUDE.md`는 지도만 담고
여기로 링크한다. 규칙 본문이 여러 곳에 흩어지면 반드시 어긋난다 — 그게 2026-09-25 개정의
이유였다(`docs/design/2026-09-25-workflow-revision.md`).

---

## 1. 작업 갈래

모든 작업은 시작 전에 셋 중 하나로 분류한다. **한 세션에 두 갈래를 섞지 않는다.**

| 갈래 | 하는 일 | 산출물 | 승인 관문 |
|---|---|---|---|
| **A — 풀 흐름** | 새 기능. 백엔드·데이터·도메인 숫자·권한에 조금이라도 닿으면 무조건 A | 스펙(`docs/specs/`) + 코드 | 스펙 승인 1회 |
| **B — 시각** | 목업과 배포 화면의 차이 보정 | 이슈 1개 + 스크린샷 대조. 새 스펙을 만들지 않는다 | 없음 (이슈로 추적) |
| **C — 버그·잔손질** | 기존 스펙의 AC를 위반한 결함, 사소한 다듬기 | 깨진 AC를 재현하는 실패 테스트 + 수정 | 없음 |

**애매하면 A.** 판단이 안 서는 채로 B나 C로 처리하면, 스펙 없이 도메인 로직이 바뀌는 사고가
난다.

- **B는 목업이 곧 스펙이다.** 목업에 없는 상태(빈·로딩·에러·경계)를 임의로 지어내지 않는다 —
  없으면 사람에게 묻는다. 디자인 토큰(색·타입·간격·모서리) 밖으로 나가지 않는다.
- **C에서 스펙에 없던 동작을 발견하면 그건 버그가 아니라 새 기능이다.** A로 전환한다.
- **한 번에 반나절이 넘는 B 작업은 B가 아니다.** 다음 마일스톤 안의 A 스펙으로 넣는다
  (`docs/ROADMAP.md`「상시 트랙」).

## 2. 흐름

```
0. 갈래 판정          A / B / C
        ↓
1. 스펙 또는 목업       A: /interview → 스펙 초안 (시나리오·AC·계약·구현 순서)
                       B: 목업 확정 (빈·로딩·에러·경계 상태 포함)
                       C: 깨진 AC를 재현하는 실패 테스트
        ↓
2. 승인                A만 해당 — 사람이 스펙을 승인한다. B·C는 승인 관문이 없다
        ↓
3. 구현                스펙의 「구현 순서」 태스크를 순서대로, TDD로
        ↓
4. 검증                아래 "완료 정의"의 명령을 전부 실행하고 출력을 확인한다
        ↓
5. PR                  CI가 초록이면 셀프 머지. 구현 중 사소한 판단은 PR 본문 「구현 중 결정」에 기록
```

**계획 문서는 없다.** 예전에는 스펙 승인 뒤 별도 계획 문서를 또 써서 승인을 한 번 더 받았다
(그 문서들은 `docs/archive/plans/`에 있다). 지금은 스펙의 「구현 순서」 절이 그 역할을 하므로
**승인 관문이 스펙 1회로 끝난다.**

### 3단계 — 구현 중 판단

**사소한 판단은 사람에게 묻지 않고 정한다.** 변수명, 에러 메시지 문구, 리팩터링 범위처럼
되돌리기 쉬운 것들이다. 정한 것은 **PR 본문의 「구현 중 결정」에 남긴다** — 다음 사람이
"왜 이렇게 짰지"를 되짚을 수 있어야 한다.

**되돌리기 어렵거나 스펙(AC)을 바꿔야 하는 판단은 멈추고 사람에게 확인받는다.** AC는 승인된
계약이므로 에이전트가 임의로 바꾸지 않는다.

## 3. 문서 수명

| 문서 | 생성 | 수정 | 삭제 |
|---|---|---|---|
| Issue | 발견 즉시 | Milestone·라벨 배정 | 머지 시 `Closes #`로 닫힘 |
| `docs/ROADMAP.md` | — | 마일스톤 편성·종료 (사용자 결정) | 안 함 |
| `docs/decisions/`(ADR) | 되돌리기 어려운 결정이 생길 때 | 대체 시 `status`만 | **안 함** |
| `docs/specs/` | A 갈래 착수 | 구현 중(AC 추가는 새 ID, 기존 ID 의미 변경 금지), 완료 시 `status` | **안 함** |
| 스펙의 「구현 순서」 절 | 스펙과 함께 | 태스크 커밋마다 체크 | `구현완료`가 되면 절 자체를 지운다 |
| `docs/GOTCHAS.md` | 함정 발견 | — | 해결되면 그 항목만 |
| 이 문서·`docs/conventions/*` | — | 마일스톤 회고, 같은 문제가 2회 반복될 때만 | 회고 때 |

**삭제하지 않는 것은 스펙과 ADR뿐이다.** 나머지는 역할이 끝나면 지우거나 닫는다 — 문서가
쌓이기만 하는 상태(2026-09-23 기준 109개·64,700줄)로 되돌아가지 않기 위해서다.

전체 저장소 구조와 각 디렉터리의 역할은 루트 `CLAUDE.md`를 참조한다.

## 4. 완료 정의

### 스펙(A) 완료
- [ ] 시나리오(무엇을·왜)와 범위 밖이 적혀 있다
- [ ] AC가 기능·엣지·실패·비기능 네 갈래를 실제로 관련된 만큼 다룬다
- [ ] 모든 AC에 유일한 ID와 리터럴 값이 있다 (금지 표현 없음 — `docs/specs/README.md` 참조)
- [ ] 경계값이 각각 별도 AC로 있다
- [ ] 에러 케이스의 HTTP 상태와 `code`가 명시돼 있다
- [ ] 「구현 순서」에 스펙의 모든 AC가 태스크로 매핑돼 있다
- [ ] 사람이 승인했다

### 코드(A·C) 완료
- [ ] `cd backend && ./gradlew clean check` 통과 (해당 시)
- [ ] `cd frontend && pnpm typecheck && pnpm lint && pnpm test && pnpm build` 통과 (해당 시)
- [ ] `./scripts/check-spec-coverage.sh` 통과
- [ ] A라면 스펙의 `status`를 `구현완료`로 변경하고 「구현 순서」 절을 지운다
- [ ] **실제로 명령을 실행하고 출력을 확인했다.** 확인 없이 "완료"라고 말하지 않는다

### 시각 보정(B) 완료
- [ ] 목업과 배포 화면을 나란히 스크린샷 대조했다
- [ ] 디자인 토큰(색·타입·간격·모서리) 밖으로 나간 값이 없다
- [ ] 이슈를 닫았다 (새 스펙·계획 문서 없음)

## 5. ★ 검증은 "출력을 찍는 것"이 아니라 "기대값과 대조하는 것"이다

명령을 돌리고 결과를 출력한 뒤 **읽지 않고 넘어가는 것이 이 프로젝트에서 가장 자주 난
사고다.** 초록이라고 말하기 전에 아래를 지킨다.

1. **숫자를 셀 거면 기대값을 먼저 말한다.** 찍힌 숫자를 보고 나서 해석하면 무엇이 나와도
   납득하게 된다.
2. **에러를 숨기지 않는다.** `2>/dev/null`은 실패를 지운다. 조용히 만들고 싶으면 종료 코드라도
   확인한다.
3. **빨간 것을 먼저 본다.** 테스트가 처음부터 통과하면 그 테스트는 아무것도 지키지 않을 수
   있다. **의도적으로 깨뜨려 빨개지는지 확인하고 되돌린다.**
4. **되돌리기 어려운 일 앞에서는 한 번 더 대조한다.** 커밋·푸시·머지·배포가 여기 해당한다.

> 자동 검증이 전부 초록인데 실제 화면이 열리지 않은 적이 있다. **초록은 "내가 검증하기로 한
> 것"이 맞다는 뜻이지 "동작한다"는 뜻이 아니다.**

## 6. 기계적 검증 — 커버리지 검사

```bash
./scripts/check-spec-coverage.sh
```

`docs/specs/`의 모든 스펙에서 `AC-XXX-NN` 형태의 ID를 추출해 `backend/src/test/`와
`frontend/src/`(e2e 포함)에서 찾는다. 하나라도 없으면 실패(exit 1)하고 누락 목록을 출력한다.
검사 강도는 스펙 `status`를 따른다 — 위 표 참조. `구현완료`가 되는 순간부터 강제되고, CI에서도
돌아간다.

## 7. 인터뷰 규칙

`/interview`는 A 갈래 스펙을 쓰기 전에 요구사항을 확정한다. 자세한 진행 순서는
[`.claude/commands/interview.md`](../../.claude/commands/interview.md).

### 기본값 표 방식

**하나씩 캐묻지 않는다.** 조사를 먼저 하고, 결정 목록 전체를 **추천값과 함께 표로 한 번에**
제시한다. 사용자는 바꾸고 싶은 항목만 짚는다.

개별로 질문하는 것은 다음 둘뿐이다.

- **추천 근거가 없는 것** — 조사로 답이 안 나오는, 순전히 취향이거나 사용자만 아는 값
- **되돌리기 어려운 것** — 스키마, 공개 범위 기본값, 데이터 마이그레이션 방향

기술적인 결정(어떤 인덱스를 쓸지, 어떤 패턴을 재사용할지)은 **묻지 않고 정한 뒤 근거를
남긴다.** 사용자가 판단할 정보가 아니다.

### 인터뷰 종료 체크리스트

아래가 전부 확인돼야 인터뷰를 끝낼 수 있다.

- [ ] **목업 필드 ↔ 계약 대조** — 화면에 그려질 값이 API 응답 필드와 전부 맞는다
- [ ] **상태별 화면** — 빈·로딩·에러·경계 상태가 전부 정의됐다
- [ ] **권한** — 이 기능에 인가 규칙이 있다면 누가 무엇을 볼 수 있는지 확정됐다
- [ ] **에러 코드** — 실패 케이스마다 HTTP 상태와 `code`가 정해졌다

## 8. 멀티 에이전트

**기본은 세션 1개 + 서브에이전트다.** 탐색은 `explorer`, 목업 대조는 `mockup-checker`, 리뷰는
`reviewer`에게 맡긴다(`.claude/agents/`). 서브에이전트는 같은 세션 안에서 컨텍스트를 아끼는
용도이지, 병렬 작업 단위가 아니다.

**동시 세션은 `--worktree`로 최대 2개까지.** 시작 전에 **공용 파일이 겹치지 않는지** 확인한다
— 겹치면 순차로 돌린다. 포트·컨테이너 충돌(백엔드 2개 금지 등)은
[`handover.md`](handover.md)「병렬 작업」을 따른다.

**백엔드·프론트 분리는 큰 기능에만 쓴다.** API 계약을 먼저 PR로 확정한 뒤(`docs/contracts/`),
백엔드 PR과 프론트 PR을 각각 `main` 기준으로 연다 — 서로를 base로 잡지 않는다(스택 PR 금지,
[`git.md`](git.md)).

## 9. 예외

- **버그 수정(C):** 기존 스펙의 AC를 위반한 것이므로, **깨진 AC를 재현하는 실패 테스트**를
  먼저 쓴다. 스펙에 없던 동작이면 그건 버그가 아니라 새 기능이니 A로 전환한다.
- **리팩터링(C):** 동작이 안 바뀌므로 기존 테스트가 그대로 통과해야 한다. 테스트를 고쳐야
  한다면 그건 리팩터링이 아니다.
- **오타·문서 수정·의존성 업데이트:** 해당 없음.
