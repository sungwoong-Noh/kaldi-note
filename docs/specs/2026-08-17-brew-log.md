# 브루잉 로그 스펙

> 2026-08-17 `/interview`로 확정. 작성 규칙은 [`docs/conventions/workflow.md`](../conventions/workflow.md).

## 무엇을

사용자가 실제로 커피를 내린 뒤, 어떤 레시피와 어떤 원두 재고로 내렸는지, 실제로 쓴 원두량·물량·물온도·분쇄도가 얼마였는지를 **실측 스냅샷**으로 기록한다. 음료 중량과 TDS를 입력하면 서버가 기존 `extraction` 도메인으로 추출 수율(EY)과 SCA 농도·추출 구간을 계산해 함께 보여준다. TDS가 없어도 기록은 온전히 저장·조회된다.

레시피(Recipe)는 설계도이고 브루잉 로그(BrewLog)는 그 설계도를 실제로 실행한 기록이다. 레시피 값을 나중에 고쳐도 이미 저장된 브루잉 로그의 실측값은 바뀌지 않는다 — 그래야 "이번엔 왜 이렇게 나왔지"를 과거 시점 그대로 비교할 수 있다.

### 범위 밖 (Non-goals)

1. **목록 조회·수정·삭제 API.** 이번 스펙은 생성(POST)과 단건 조회(GET)만 다룬다. 목록·수정·삭제는 후속 스펙 몫이다.
   > **2026-08-19 정정:** 후속 스펙 `docs/specs/2026-08-19-list-query-api.md`에서 전부 구현했다. 그 과정에서 **이 스펙의 단건 조회 동작도 바뀌었다** — `brew_logs.deleted_at`이 추가되어 `GET /api/v1/brew-logs/{id}`에 `deleted_at IS NULL` 조건이 붙는다. 소프트 삭제된 로그는 `404 NOT_FOUND`다(`AC-BLEDIT-13`).
2. **`brew_log_steps`(실제 푸어 기록).** 타이머 기능과 함께 후속 스펙에서 다룬다. 이번 스펙의 어떤 API도 스텝 단위 기록을 받지 않는다.
3. **`brew_log_flavor_notes`(실제 컵노트).** `bean_product_flavor_notes`와 같은 N:M 패턴이지만 이번 스펙에서는 만들지 않는다.
4. **사진 첨부.** `attachments` 연동은 Plan 3(Object Storage)이다.
5. **공개범위(visibility) 인가 로직.** `visibility` 컬럼은 스키마에 포함하지만 값은 항상 `PRIVATE`로 고정하고 요청으로 받지 않는다. GET은 레시피 스펙과 동일하게 **소유자 전용 403**으로 제한한다. FRIENDS/PUBLIC 판정은 공개범위 인가 스펙의 몫이다.
6. **원두 재고 자동 차감.** 브루잉 로그 생성으로 `bean_batches.remaining_g`을 자동으로 줄이지 않는다. 원두 재고 스펙에서 이미 "부가기능"으로 제외하기로 결정한 사항을 유지한다.
7. **즉흥 추출(레시피 없는 기록).** 설계 문서는 `recipe_id`를 nullable로 열어뒀지만, 이번 스펙은 `recipe_id`·`bean_batch_id` 둘 다 **필수**로 좁힌다. 즉흥 추출 허용은 별도 결정이 필요하면 그때 연다.

## 왜

레시피만으로는 "그래서 오늘 내린 커피는 어땠는가"를 알 수 없다. 같은 Kasuya 4:6 레시피도 원두 컨디션·분쇄도 미세 조정에 따라 결과가 매번 다르다. 이 차이를 감이 아니라 실측값과 EY/SCA 좌표로 남겨야, 다음에 같은 레시피를 내릴 때 "지난번엔 분쇄를 더 곱게 했더니 좋았다"는 판단이 가능해진다.

TDS는 리프랙토미터가 있어야 재는데, 우리는 없다. `extraction` 스펙이 이미 세운 원칙(TDS 없이도 앱이 온전히 동작해야 한다)을 브루잉 로그도 그대로 물려받는다.

## 용어

| 용어 | 정의 |
|---|---|
| 실측 스냅샷 | 레시피의 계획값과 별개로, 실제로 이번에 쓴 값. 레시피가 나중에 바뀌어도 불변 |
| 로스팅 후 경과일(daysOffRoast) | `brewedAt` 날짜에서 원두 재고의 `roastedAt`을 뺀 일수. 생성 시점에 계산해 스냅샷으로 저장 |
| 디게싱 상태(degassingStatus) | 원두 재고 스펙과 동일한 3단계 판정. `daysOffRoast` 기준으로 생성 시점에 함께 스냅샷 저장 |
| 브루 비율(brewRatio) / 추출 수율(EY) / 농도·추출 구간 | `extraction` 스펙(`docs/specs/2026-08-14-extraction-analysis.md`)의 정의를 그대로 따른다. 저장하지 않고 조회 시점마다 재계산한다 |

### 신설 ErrorCode

없음. 기존 `INVALID_REQUEST`(400)·`INVALID_BREW_MEASUREMENT`(400, `docs/specs/2026-08-14-extraction-analysis.md`)·`UNAUTHORIZED`(401)·`FORBIDDEN`(403)·`NOT_FOUND`(404)를 재사용한다.

## 어떻게 동작 — 인수 조건

> 아래 조건은 모두 **원두량 15g / 물 250g**(레시피·브루잉 로그 공통), **userGrinderId → C40, `micronsPerClick=30`, `zeroPointOffsetClicks=0`**을 전제로 한다. 별도 명시가 없으면 이 값을 쓴다.

### 정상 동작

#### AC-BREW-01 · 필수 값만으로 브루잉 로그가 생성된다

- **Given** 인증된 사용자 소유의 레시피·재고·그라인더
- **When** `recipeId`, `beanBatchId`, `brewedAt`, `actualDoseG=15.0`, `actualWaterG=250.0`, `actualWaterTempC=92.0`, `userGrinderId`, `actualGrindSettingValue=22.0`만 담아 `POST /api/v1/brew-logs`
- **Then** HTTP `201`. `visibility="PRIVATE"`, `actualGrindMicronEstimated=660`, `beverageWeightG`·`tdsPercent`·`rating`·관능 항목은 모두 `null`
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-02 · 음료 중량과 TDS가 있으면 EY/구간이 함께 반환된다

- **Given** AC-BREW-01과 동일 전제
- **When** `beverageWeightG=240.0`, `tdsPercent=1.25`를 추가해 생성
- **Then** HTTP `201`, `extractionYieldPercent=20.0`, `strengthZone="IDEAL"`, `extractionZone="IDEAL"`, `diagnosis`에 `"이상적"` 포함
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-03 · TDS가 없으면 수율과 구간이 모두 null이다

- **Given** AC-BREW-01과 동일 전제
- **When** `beverageWeightG=240.0`만 주고 `tdsPercent`는 생략해 생성
- **Then** HTTP `201`, `extractionYieldPercent`·`strengthZone`·`extractionZone`이 모두 `null`, `diagnosis`에 `"TDS"` 포함
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-04 · 무단계 그라인더를 쓰면 마이크론 추정치만 null이고 생성은 성공한다

- **Given** `microns_per_click`이 없는(STEPLESS) 그라인더를 가리키는 `userGrinderId`
- **When** 나머지는 AC-BREW-01과 동일하게 생성
- **Then** HTTP `201`, `actualGrindMicronEstimated=null`
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-05 · daysOffRoast와 degassingStatus는 brewedAt 기준으로 생성 시점에 계산된다

- **Given** `roastedAt`이 `brewedAt` 날짜로부터 6일 전인 재고
- **When** 생성
- **Then** HTTP `201`, `daysOffRoast=6`, `degassingStatus="IDEAL"`
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-06 · 단건 조회는 저장된 값과 재계산된 EY/SCA를 함께 반환한다

- **Given** AC-BREW-02로 생성된 브루잉 로그
- **When** 소유자가 `GET /api/v1/brew-logs/{id}`
- **Then** HTTP `200`, 생성 응답과 동일한 `extractionYieldPercent=20.0` 등 EY/SCA 값
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-07 · 레시피의 doseG를 나중에 수정해도 기존 브루잉 로그의 actualDoseG는 변하지 않는다

- **Given** `doseG=15.0`인 레시피로 만든 브루잉 로그(`actualDoseG=15.0`)
- **When** 소유자가 그 레시피를 `doseG=20.0`으로 `PUT /api/v1/recipes/{id}` 수정한 뒤, 브루잉 로그를 다시 조회
- **Then** `actualDoseG`는 여전히 `15.0`이다 (**필수 회귀 테스트** — 스냅샷 불변성)
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-08 · BeanBatch를 삭제해도 daysOffRoast·degassingStatus는 남는다

- **Given** `daysOffRoast=6`, `degassingStatus="IDEAL"`로 생성된 브루잉 로그
- **When** 소유자가 그 재고를 `DELETE /api/v1/bean-batches/{id}` 한 뒤, 브루잉 로그를 다시 조회
- **Then** HTTP `200`, `daysOffRoast=6`, `degassingStatus="IDEAL"` 그대로 (**필수 회귀 테스트**)
- **검증** API 테스트 `BrewLogControllerTest`

#### AC-BREW-09 · 관능 평가 필드를 전부 생략해도 생성된다

- **Given** AC-BREW-01과 동일 전제
- **When** `rating`·`acidity`·`sweetness`·`body`·`bitterness`·`aftertaste`·`overallNote`를 전부 생략해 생성
- **Then** HTTP `201`
- **검증** API 테스트 `BrewLogControllerTest`

## 열어둔 결정

- **즉흥 추출(레시피 없는 기록) 허용 여부** — 이번 스펙은 `recipeId`를 필수로 좁혔다. 필요해지면 별도 인터뷰로 nullable 전환을 다시 연다.
- **목록 조회·수정·삭제 API** — 다음 스펙에서 다룬다. 특히 수정 시 EY 재계산 범위(실측값만 바꿀 수 있는지, 관능 평가만 나중에 추가하는 플로우를 허용할지)는 그때 결정한다.
- **`brew_log_steps`·`brew_log_flavor_notes`** — 타이머 기능·컵노트 통계가 실제로 필요해지는 시점에 별도 스펙으로 연다.
- **공개범위 인가(FRIENDS/PUBLIC)** — 레시피와 함께 별도 스펙에서 다룬다. 그때 `visibility`를 요청 필드로 열지도 같이 정한다.
