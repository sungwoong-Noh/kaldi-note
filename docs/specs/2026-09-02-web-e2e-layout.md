# 실제 브라우저로 레이아웃 불변식 고정 (E2E) 스펙

> 2026-09-02 `/interview`로 확정. 작성 규칙은 [`docs/conventions/workflow.md`](../conventions/workflow.md).
> **모든 인수 조건은 자동화된 테스트로 옮길 수 있어야 한다.**

## 무엇을

Playwright로 실제 Chromium을 띄워 **11개 화면의 레이아웃 불변식 셋을 검사한다.** 탭바가 화면 하단에 붙는가, 가로 스크롤이 생기지 않는가, 탭바가 본문 끝을 가리지 않는가. 화면이 부르는 API는 브라우저에서 모두 가로채 고정 픽스처로 답하므로 **백엔드도 PostgreSQL도 띄우지 않는다.**

### 범위 밖 (Non-goals)

- **사용자 여정 E2E.** 로그인 → 포크 → 기록 같은 흐름을 통짜로 고정하지 않는다. 그건 백엔드를 CI에 띄워야 하고, 이 스펙의 목적(jsdom이 못 보는 것)과 다르다.
- **스크린샷 시각 회귀.** 화면 전체를 이미지로 비교하지 않는다. 갱신 부담만 크다는 이유로 두 번 미뤄진 방식이다(`2026-08-21-web-recipe-read.md`, `2026-08-30-web-recipe-write.md`).
- **운영 URL 스모크.** `kaldi-note.today`에 대고 돌리지 않는다. 카카오 실계정 로그인이 필요하다.
- **실제 백엔드 연동.** 요청은 전부 스텁이다. 백엔드 계약이 바뀌어도 이 스위트는 잡지 못한다 — 그건 jsdom 테스트의 픽스처와 통합 테스트가 맡는다.
- **데스크톱 뷰포트.** 「탭바를 넓은 화면에서 다르게 그릴지」가 앱 셸 스펙에 열어둔 결정으로 남아 있다. 그 결정 전에 고정하면 결정을 미리 묶는다.
- **터치 타깃 최소 크기 검사.** 젖은 손 조작과 직결되지만 이번 분량에 넣지 않는다.
- **세션 복구 로직.** 로그인도 가로채기로 처리하므로 refresh 왕복 자체는 검사하지 않는다. jsdom 테스트가 이미 덮는다.
- **`/login`과 `/auth/callback`.** 전자는 입력칸 하나짜리이고 후자는 인가코드를 넘기는 중간 화면이라 검사할 레이아웃이 없다.

## 왜

**2026-09-02 수동 확인에서 테스트 279개가 초록인 채로 실물이 두 군데 틀려 있었다.**

탭바는 `sticky bottom-0`만 갖고 있어 콘텐츠가 짧은 화면에서 y=276 부근, 즉 화면 한가운데 떠 있었다(뷰포트 812). 앱 셸 스펙의 인수 조건 31개 중 **위치를 못박은 것이 하나도 없었기 때문에** 아무도 보지 않았다. 사람이 브라우저를 띄워 좌표를 재고 나서야 드러났다.

지금 그 조건은 앱 셸 스펙(`docs/specs/2026-09-01-web-shell.md`)의 「콘텐츠가 짧아도 탭바가 화면 하단에 놓인다」로 막혀 있으나, **jsdom은 레이아웃을 계산하지 않아 클래스(`mt-auto`)가 있는지만 본다.** `mt-auto`를 지우면 잡히지만, 다른 이유로 탭바가 밀려나면 못 잡는다.

이 스위트가 없으면 같은 부류의 결함이 계속 사람의 눈에만 의존한다. 그리고 수동 확인은 밀린다 — 이번에 12개가 세 스펙에 걸쳐 밀려 있었다.

## 용어

| 용어 | 정의 |
|---|---|
| 레이아웃 불변식 | 화면 내용과 무관하게 모든 대상 화면에서 지켜져야 하는 기하학적 규칙 |
| 대상 화면 | 이 스위트가 검사하는 11개 경로. 아래 표에 고정한다 |

## 실행 환경

| 항목 | 값 |
|---|---|
| 브라우저 | Chromium (Playwright 번들) |
| 뷰포트 | **360 × 800** |
| 대상 서버 | `next start` — `pnpm build` 산출물 |
| 허용 오차 | **1px** |
| 재시도 | **0회** |
| 실패 시 | 그 화면의 스크린샷을 아티팩트로 남긴다 |

**뷰포트를 360×800으로 정한 근거:** 360px과 375px이 모바일 트래픽의 절반 이상이고, 360×800·390×844·393×852 셋이 60%를 차지한다. 360px은 현실적 최소 폭이며 가로 스크롤은 폭이 좁을수록 먼저 드러난다. 넓은 폭에서만 터지는 결함은 이 표본으로 잡지 못한다 — 그건 「데스크톱 뷰포트」를 범위 밖으로 둔 대가다.

## 어떻게 동작 — 인수 조건

> 좌표는 CSS 픽셀이다. 모든 비교는 1px 오차를 허용한다.

### 정상 동작

#### AC-WEBLAYOUT-01 · 탭바가 뷰포트 하단에 붙는다

- **Given** 360×800 뷰포트에서 탭바가 있는 7개 화면(위 표의 1~7)을 각각 연다
- **When** `nav[aria-label="주요 화면"]`의 경계 상자를 읽는다
- **Then** `y + height`가 `800`과의 차이가 `1` 이하다
- **검증** E2E `e2e/layout.spec.ts`

#### AC-WEBLAYOUT-02 · 가로 스크롤이 생기지 않는다

- **Given** 360×800 뷰포트에서 대상 화면 11개를 각각 연다
- **When** `document.documentElement.scrollWidth`를 읽는다
- **Then** 그 값이 `361` 이하다 (뷰포트 폭 `360` + 허용 오차 `1`)
- **검증** E2E `e2e/layout.spec.ts`

#### AC-WEBLAYOUT-03 · 탭바가 본문 끝을 가리지 않는다

- **Given** 360×800 뷰포트에서 탭바가 있는 7개 화면을 각각 열고 문서 맨 아래까지 스크롤한다
- **When** `main`의 아랫변과 `nav`의 윗변을 읽는다
- **Then** `main`의 아랫변이 `nav`의 윗변보다 `1`을 초과해 크지 않다
- **검증** E2E `e2e/layout.spec.ts`

#### AC-WEBLAYOUT-04 · 스텁되지 않은 요청이 나가면 실패한다

- **Given** 대상 화면 11개를 각각 연다
- **When** 브라우저가 보낸 요청 중 `**/api/v1/**` 패턴에 걸렸으나 스텁 표에 없는 것을 센다
- **Then** 그 수가 `0`이다
- **검증** E2E `e2e/layout.spec.ts`

> 이 조건은 「백엔드 없이 돈다」는 이 설계의 전제를 지킨다. 화면이 새 API를 부르기 시작하면 스텁이 없어 화면이 비어 보일 뿐 조용히 통과할 수 있는데, 이 조건이 즉시 빨간불을 낸다.

### 경계값

#### AC-WEBLAYOUT-10 · 1px 어긋난 것은 통과한다

- **Given** `nav`의 아랫변이 `799`이거나 `801`이다
- **When** AC-WEBLAYOUT-01의 판정을 적용한다
- **Then** 통과한다
- **검증** E2E 헬퍼의 단위 테스트 `e2e/tolerance.spec.ts`

#### AC-WEBLAYOUT-11 · 2px 어긋난 것은 실패한다

- **Given** `nav`의 아랫변이 `798`이거나 `802`다
- **When** AC-WEBLAYOUT-01의 판정을 적용한다
- **Then** 실패한다
- **검증** E2E 헬퍼의 단위 테스트 `e2e/tolerance.spec.ts`

> 경계값을 화면이 아니라 **판정 함수**에서 검사한다. 실제 화면을 1px씩 어긋나게 만들 방법이 없기 때문이다. 판정 로직을 순수 함수로 뽑아 두 조건이 그것을 직접 부른다.

## 열어둔 결정

- **데스크톱 뷰포트 추가.** 앱 셸 스펙의 「탭바를 넓은 화면에서 다르게 그릴지」가 정해지면 그때 함께 정한다.
- **터치 타깃 최소 크기.** 젖은 손 조작이 실제로 불편해지면 그때 기준치를 정해 이 스위트에 더한다.
- **사용자 여정 E2E.** 백엔드를 CI에 띄울 이유가 생기면(예: 계약 회귀가 실제로 발생) 그때 별도 스펙으로 다룬다.
- **앱 셸 스펙의 클래스 검사 조건을 남길지.** 이 스위트가 좌표를 보게 됐으니 중복으로 볼 수도 있으나, 층이 달라 당분간 둘 다 남긴다. E2E가 안정적으로 도는 것을 몇 세션 확인한 뒤 재검토한다.
