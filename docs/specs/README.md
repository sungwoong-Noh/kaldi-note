# 스펙

**AC(인수 조건)를 가진 문서만 여기 둔다.** "왜 이 구조인가" 같은 설명은 `docs/design/`이 맡는다.

작업 갈래(A/B/C)와 전체 흐름은 [`docs/conventions/workflow.md`](../conventions/workflow.md)가
정한다. 이 문서는 **스펙 한 편을 어떻게 쓰는가**만 다룬다.

---

## 파일명

`docs/specs/YYYY-MM-DD-<기능명>.md` · 템플릿: [`TEMPLATE.md`](TEMPLATE.md)

## frontmatter

```yaml
id: <대문자 약어. AC ID의 접두어가 된다. 예: GRIND, RECIPE>
title: <기능 이름>
status: 초안
milestone: <docs/ROADMAP.md의 마일스톤. 예: M1. 상시 트랙(버그·시각 보정)이면 비워둔다>
supersedes: <이 스펙이 대체하는 이전 스펙 경로. 없으면 비워둔다>
```

`status`는 넷 중 하나다.

| status | 의미 | 커버리지 검사 |
|---|---|---|
| `초안` | 인터뷰 중이거나 승인 전 | 건너뜀 |
| `승인` | 승인됐지만 구현 전 | 건너뜀 |
| `구현중` | 「구현 순서」의 일부 태스크가 끝남 | 경고만 |
| `구현완료` | 「구현 순서」 전체 완료, 수동 확인 중 차단형이 없음 | 누락 시 실패 |

## 스펙은 인터뷰로 만든다

```
/interview <만들려는 기능 한 줄>
```

`/interview`는 **기본값 표 방식**을 쓴다 — 조사한 뒤 결정 목록 전체를 추천값과 함께 한 번에
제시하고, 사용자는 바꿀 것만 짚는다. 개별로 캐묻는 것은 **추천 근거가 없는 것**과
**되돌리기 어려운 것**뿐이다. 상세 규칙은 [`.claude/commands/interview.md`](../../.claude/commands/interview.md).

**요구사항을 추측해서 스펙을 쓰지 않는다.** 인터뷰가 끝나면 결정 목록과 AC 초안을 보여주고
승인을 받은 뒤에 파일을 만든다.

---

## 스펙의 절 구성

| 절 | 답하는 것 |
|---|---|
| **시나리오** | 무엇을 · 왜. 누가 언제 쓰는가. 범위 밖(Non-goals)도 여기 적는다 |
| **AC** | 어떻게 동작 — 기능 · 엣지 · 실패 · 비기능 넷 전부, 각각 ID + 리터럴 값 |
| **계약** | API라면 `docs/contracts/`의 OpenAPI 조각을 가리킨다. 없으면 절을 지운다 |
| **구현 순서** | 태스크 단위 실행 계획. 예전의 별도 계획 문서(`docs/archive/plans/`)가 이 절로 흡수됐다 |
| **수동 확인** | 자동화할 수 없는 것만. 차단형(`★`)/비차단형 구분은 [`verification.md`](../conventions/verification.md) |

**별도 계획 파일을 만들지 않는다.** 스펙 하나가 승인되면 그걸로 구현에 들어간다 —
승인 관문이 스펙 1회로 끝난다(예전에는 스펙 승인 + 계획 승인 2회였다).

## ★ 인수 조건은 기계적으로 검증 가능해야 한다

이 규칙 하나가 나머지 전부보다 중요하다. **모든 인수 조건은 자동화된 테스트로 옮길 수 있어야
한다.** 옮길 수 없다면 그건 인수 조건이 아니라 소망이다 — `## 수동 확인` 절로 보낸다.

### AC는 네 갈래를 전부 다룬다

| 갈래 | 예 |
|---|---|
| **기능** | 정상 입력에서 기대하는 동작 |
| **엣지** | 경계값. `18.0`이 포함인지 `17.9`가 제외인지 각각 조건으로 쓴다 |
| **실패** | 잘못된 입력, 권한 없음. HTTP 상태와 `code`를 명시한다 |
| **비기능** | 성능·용량 제약이 있다면(OCI 2 OCPU/12GB, Workers CPU 10ms 등) 리터럴 값으로 |

### 형식

```markdown
#### AC-GRIND-01 · C40 22클릭은 660마이크론이다

- **Given** 클릭당 30µm, 영점 보정 0인 그라인더
- **When** 설정값 22로 마이크론을 계산하면
- **Then** 결과는 정확히 `660`이다
- **검증** 단위 테스트 `GrindConverterTest`
```

- **ID는 `AC-<기능>-<번호>`.** 유일해야 하고, 한 번 부여하면 바꾸지 않는다. 테스트가 이 ID로
  스펙을 역참조한다.
- **값은 리터럴로 적는다.** "적절한 값"이 아니라 `660`이다.
- **검증 수단을 명시한다.** 단위 테스트 / 통합 테스트 / API 테스트 / e2e 중 무엇인지.

### 쓰면 안 되는 표현

> 적절히 · 적당한 · 빠르게 · 충분히 · 유연하게 · 필요시 · 등등 · 기타 · 사용자 친화적 ·
> 직관적 · 자연스럽게 · 잘 동작한다

```markdown
❌ 분쇄도 환산 결과를 적절히 반올림한다
✅ 대상 설정값은 소수 첫째 자리에서 HALF_UP으로 반올림한다. 900µm ÷ 22µm/click = 40.909... → `40.9`
```

### 자동으로 검증할 수 없는 것

시각 디자인, 문구의 자연스러움 같은 것은 정직하게 `## 수동 확인` 절에 따로 적는다. AC에 섞지
않는다. 섞으면 "기계적 검증"이라는 기준 자체가 무너진다.
