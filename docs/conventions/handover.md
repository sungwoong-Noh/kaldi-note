# 세션 핸드오버

작업은 **세션 단위로 나뉘고, 세션마다 다른 에이전트가 붙는다.** 새 에이전트는 이전 세션의 대화를 보지 못한다. 저장소에 남은 것만 볼 수 있다.

```
세션 시작:  /resume     → 상태 파악 + 테스트 실행 + 할 일 제안
세션 종료:  /handover   → 테스트 확인 + 체크박스 갱신 + JOURNAL 기록 + 커밋
```

---

## 세션 종류와 흐름

세션은 성격에 따라 셋으로 나뉜다. **한 세션에 두 성격을 섞지 않는다.**

| 세션 | 하는 일 · 산출물 | 브랜치 | 계획 문서 | 쓰는 스킬 |
|---|---|---|---|---|
| **설계** | `/interview` → 스펙 → 계획<br>`docs/specs/`, `docs/plans/` | `docs/spec-<기능>` | **본문만** | `superpowers:brainstorming`<br>`superpowers:writing-plans` |
| **구현** | 계획의 태스크 실행 (TDD)<br>코드 + 테스트 | `feat/<기능>` | **체크박스만** | `superpowers:test-driven-development`<br>`superpowers:verification-before-completion`<br>`superpowers:systematic-debugging`<br>`/code-review`, `/simplify`<br>`/security-review` (인증 태스크 후) |
| **디자인** | IA, 와이어프레임<br>`docs/design/` | `design/<이름>` | 건드리지 않음 | `pencil` MCP (`.pen` 와이어프레임)<br>`dataviz` (SCA 차트)<br>`ui-ux-pro-max:ui-styling` |

**계획 문서의 체크박스는 구현 세션만 건드린다.** 설계 세션이 본문을, 구현 세션이 체크박스를 담당하면 같은 파일을 고쳐도 충돌이 거의 나지 않는다.

### 쓰지 말 것 — 이 프로젝트와 충돌하는 스킬

| 스킬 | 왜 안 되는가 |
|---|---|
| `superpowers:using-git-worktrees` | **항상** 격리 워크스페이스를 만든다. 이 프로젝트는 순차 작업이면 worktree가 불필요하고, 백엔드가 여러 워크스페이스로 갈라지면 5432 포트와 Testcontainers 재사용 컨테이너를 놓고 충돌한다 |
| `superpowers:executing-plans` | Step 1의 첫 항목이 위 스킬 호출이다. 계획을 실행할 때마다 worktree를 만들게 된다 |
| `superpowers:subagent-driven-development` | 태스크마다 서브에이전트를 띄운다. 이 프로젝트는 `/resume`·`/handover`로 세션을 나누는 쪽을 택했다. 둘을 섞으면 체크박스와 JOURNAL을 누가 갱신하는지가 흐려진다 |

**병렬 작업의 worktree는 `EnterWorktree`로 직접 만든다.** 위 "병렬 작업" 절 참조.

### 스킬을 새로 만들지 않는다

커피 도메인 규칙(반올림 스케일, SCA 상수, 단위 네이밍)을 프로젝트 전용 스킬로 뽑고 싶어질 수 있다. **하지 마라.** 그건 이미 `backend/CLAUDE.md`에 있고, 스킬로 또 만들면 두 곳이 어긋난다. 이 프로젝트가 계속 피해온 실패 방식이다.

### 무엇부터 할지 정하는 법

```
만들려는 기능에 계획 문서가 이미 있는가?

├─ 있다  →  구현 세션에서 바로 실행
│           (예: Plan 1의 Task 1~11. 스펙도 이미 있으므로 인터뷰 불필요)
│
└─ 없다  →  설계 세션:  /interview → 스펙 승인 → 계획 작성 → 승인
            구현 세션:  태스크 실행
```

### 인터뷰와 구현을 같은 세션에서 하지 않는 이유

컨텍스트 성격이 다르다. 인터뷰는 사람과의 대화로, 구현은 코드로 컨텍스트를 채운다.
**한 세션에 둘 다 넣으면 정작 구현 중간에 컨텍스트가 찬다.** 설계 세션의 산출물은 문서라 핸드오버가 깨끗하므로 나누는 쪽이 항상 이득이다.

### 병렬 작업 — worktree

**같은 디렉터리에서 두 세션을 동시에 열지 않는다.** 한쪽이 `git switch`를 하면 다른 쪽 발밑에서 파일이 바뀐다. 커밋하지 않은 변경이 뒤섞이고, 어느 세션이 무엇을 깨뜨렸는지 추적이 불가능해진다.

동시에 작업하려면 **각 세션이 자기 worktree를 갖는다.**

```
세션 시작 시 EnterWorktree 호출 → .claude/worktrees/<이름>/ 에 격리된 작업 공간 생성
```

- **순차 작업**(한 번에 한 세션)이면 worktree가 필요 없다. 브랜치 전환으로 충분하다
- **동시 작업**이면 반드시 worktree를 만든다. `/resume`이 이를 확인한다

### 병렬로 돌려도 되는 조합

| 조합 | 가능? | 이유 |
|---|---|---|
| 백엔드 1 + 프론트 1 + 디자인 1 | ✅ | 건드리는 파일도 포트도 다르다 |
| 디자인 + 아무거나 | ✅ | `docs/design/`만 고치고 서버를 띄우지 않는다 |
| **백엔드 2개** | ❌ | 아래 참조 |
| **프론트 2개** | ❌ | dev server 3000 포트 충돌 |

**백엔드 세션은 하나만 돌린다.** 이유가 둘이다:

1. `docker-compose.yml`의 PostgreSQL이 호스트 **5432 포트를 고정**으로 쓴다
2. `TestcontainersConfiguration`이 **`.withReuse(true)`** 라 컨테이너를 재사용한다. 두 세션이 동시에 테스트를 돌리면 Flyway 마이그레이션과 테스트 데이터가 섞여서, **실패 원인을 자기 코드에서 찾게 된다**

정말 백엔드를 둘 돌려야 한다면 `withReuse`를 끄고 compose의 포트 매핑을 분리해야 한다. 그 비용을 치를 만한 상황은 거의 없다.

### 언제 세션을 끝내는가

- 태스크를 완료했을 때
- **컨텍스트가 15~20% 남았을 때** — 가득 찬 뒤에 `/handover`를 부르면 늦다. 검증 실행·문서 갱신·커밋·PR 생성에 컨텍스트가 필요하다
- 막혀서 사람의 판단이 필요할 때 (이때는 JOURNAL에 막힌 지점을 반드시 남긴다)

## 무엇이 어디에 남는가

| 정보 | 저장 위치 | 이유 |
|---|---|---|
| **어디까지 했나** | `docs/plans/*.md`의 `- [ ]` 체크박스 | **단일 진실 원천.** 별도 진행표를 만들면 이중 관리가 되고 반드시 어긋난다 |
| **왜 그렇게 했나** | `docs/JOURNAL.md` | 체크박스가 못 담는 것 — 막힌 지점, 계획과 달라진 이유, 확인된 가정 |
| **무엇을 만들기로 했나** | `docs/specs/`, `docs/plans/` | 변하지 않는 계약 |
| **어떤 코드를 썼나** | git 히스토리 + PR | |

**핸드오버에서 실제로 깨지는 건 "어디까지"가 아니라 "왜"다.** 체크박스는 위치를 알려주지만, "Task 7에서 `MockRestServiceServer`가 안 돼서 다른 방식으로 갔다"는 남지 않는다. 그래서 JOURNAL이 있다.

## 브랜치와 PR

**세션 1개 = 브랜치 1개 = PR 1개.** 한 세션에서 태스크를 여러 개 진행해도 브랜치와 PR은 하나다.

```
feat/brew-log                 구현 세션 — 그 세션에서 한 태스크 전부
feat/recipe-crud
docs/spec-recipe              설계 세션 — 스펙·계획 작성
design/recipe-editor          디자인 세션
```

- 구현 브랜치명은 **기능 단위**로 짓는다. 태스크 경계는 **커밋 1개 = 태스크 1개**로 남기고, 커밋 메시지에 무엇을 왜 했는지 적는다.
- **태스크마다 브랜치를 새로 만들어 스택하지 않는다.** 이유는 [`git.md`의 "스택 PR을 쓰지 않는다"](git.md) 참조 — 두 번 사고가 났다.
- 세션이 끝나면(진행한 태스크의 Step 전부 체크 + 테스트 초록) PR을 **하나** 만든다. PR 본문의 "관련"에 계획 문서와 이번에 끝낸 태스크 번호를 전부 적는다.
- **설계·디자인 세션도 PR을 거친다.** 문서만 바뀌어도 마찬가지다 — 스펙과 계획은 이후 모든 구현의 근거이므로, 리뷰 없이 들어가면 안 된다. PR 본문에 **무엇을 왜 결정했는지** 적는다.
- **CI가 초록이어야 머지한다.** Squash and merge.
- 세션이 태스크 중간에 끝나도 **브랜치는 푸시해둔다.** 다음 세션이 이어받는다.

> **예외 없음.** `main`에 직접 커밋하지 않는다. 저장소 부트스트랩 시점의 커밋 5개(`c625b2b`~`359c41a`)는 이 규칙이 정해지기 전에 `main`으로 직행했다. 그 히스토리를 보고 "문서는 직접 커밋해도 된다"고 판단하지 말 것.

## 세션 시작 — `/resume`

새 세션은 **반드시 `/resume`으로 시작한다.** 커맨드가 하는 일:

1. `git status`, `git branch --show-current`, `git log --oneline -5` — 어디에 있나
2. `docs/JOURNAL.md`의 최근 항목 — 왜 그 상태인가
3. 계획 문서에서 **첫 미체크 태스크** — 무엇을 할 차례인가
4. **테스트 실행** — 지금 초록인가
5. 상태 요약 + 이번 세션에서 할 일 제안 → 승인 후 시작

### 4번이 핵심이다

**초록이라고 가정하고 시작하지 않는다.** 앞 세션이 깨진 상태로 끝났을 수 있고, 그걸 모르면 앞 세션의 실패를 내 작업 탓으로 오해하며 시간을 날린다.

빨간 상태로 시작하게 되면, **그 사실을 먼저 보고하고** 고칠지 이어서 진행할지 사람에게 확인받는다.

## 세션 종료 — `/handover`

작업을 멈추기 전에 **반드시 호출한다.** 커맨드가 하는 일:

1. **검증 실행** — `./gradlew clean check` + `./scripts/check-spec-coverage.sh`
2. **체크박스 갱신** — 실제로 끝낸 Step만 `- [x]`로. 안 한 것을 채우지 않는다
3. **JOURNAL 항목 추가**
4. **커밋 + 푸시**
5. 태스크가 끝났으면 **PR 생성**

### 태스크 중간에 끝날 때

흔한 일이고 문제없다. 다만:

- **태스크 전체 체크박스를 채우지 않는다.** 끝낸 Step만 체크한다
- JOURNAL에 **"Task N Step 3까지. 다음은 Step 4"** 를 명시한다
- 막혀서 멈춘 거라면 **무엇에 막혔는지, 무엇을 시도했는지**를 쓴다. 이게 없으면 다음 세션이 같은 벽에 다시 부딪힌다
- 브랜치를 푸시한다. PR은 만들지 않는다(태스크 미완이므로)

### 테스트가 빨간 채로 끝나야 할 때

가능하면 피하되, 불가피하면:

- **커밋 메시지 제목에 `WIP:`를 붙인다**
- JOURNAL에 **어떤 테스트가 왜 실패하는지** 정확히 쓴다
- PR을 만들지 않는다

## JOURNAL 작성 규칙

`docs/JOURNAL.md`는 **최신 항목이 위**로 오게 쓴다(역순). **append-only — 과거 항목을 고치지 않는다.**

```markdown
## 2026-08-15 · Task 2 — grind 순수 도메인

**브랜치:** `feat/grind` · **PR:** #3 (머지됨)
**상태:** 완료

### 한 일
- `GrindSpec`·`GrindConverter`·예외 2종 구현, 테스트 18개 통과

### 발견한 것
- Boot 4에서 `@ServiceConnection` 경로는 그대로였다 (계획의 가정 2번 해소)
- `BigDecimal.max()`가 스케일을 유지해서 `effectiveMinSetting()` 결과가
  `0.00`으로 나온다. `isEqualByComparingTo`를 써야 테스트가 통과한다

### 다음 세션에게
- Task 3부터. `extraction`은 `grind`와 독립이라 참고할 것 없음
- `ErrorCode`는 Task 5에서 만든다. Task 3에서 미리 만들지 말 것
```

### 쓸 것 / 쓰지 말 것

| 쓴다 | 쓰지 않는다 |
|---|---|
| 계획과 **달라진** 점과 그 이유 | 계획에 그대로 있는 내용 (중복) |
| 막힌 지점과 시도한 것 | "잘 진행됨" 같은 내용 없는 문장 |
| 확인·반증된 가정 | 코드 자체 (git이 기억한다) |
| 다음 세션이 모르면 헤맬 것 | 소감 |

**항목 하나가 15줄을 넘으면 대부분 계획 문서에 있어야 할 내용이다.** 계획을 고치고 JOURNAL에는 "계획 N절 수정함"만 남긴다.

## 계획과 실제가 어긋났을 때

구현하다 보면 계획이 틀렸다는 게 드러난다. 그때:

1. **계획 문서를 고친다.** 코드만 다르게 짜고 계획을 방치하지 않는다
2. JOURNAL에 **무엇을 왜 고쳤는지** 남긴다
3. 스펙(AC)까지 바꿔야 하는 거라면 **멈추고 사람에게 확인받는다.** AC는 승인된 계약이므로 에이전트가 임의로 바꾸지 않는다

문서와 코드가 어긋난 채로 세션을 넘기는 것이 이 프로젝트에서 가장 비싼 실수다. 다음 세션은 문서를 믿고 시작하기 때문이다.
