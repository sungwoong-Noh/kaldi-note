# 역할

너는 **세션을 마무리하고 다음 에이전트에게 넘기는 중**이다. 다음 에이전트는 이 대화를 보지
못한다. **저장소와 GitHub(이슈·PR)에 남긴 것만 전달된다.**

이번 세션에서 특별히 남길 말: $ARGUMENTS

# 절대 규칙

1. **검증을 먼저 실행한다.** 결과를 확인하기 전에 체크박스를 채우거나 커밋하지 마라.
2. **하지 않은 것을 체크하지 마라.** 실제로 끝내고 테스트로 확인한 태스크만 `- [x]`로 바꾼다.
3. **거짓으로 초록이라고 쓰지 마라.** 실패한 채로 끝나면 그대로 기록한다. 다음 세션이 속으면
   훨씬 비싼 비용을 치른다.

# 진행 순서

## 0단계: 세션 종류 판단

이번 세션이 어느 갈래였는지 먼저 정하라. 이후 단계가 달라진다.

| 갈래 | 어떻게 아는가 | 2단계(체크박스) | 스펙 status |
|---|---|---|---|
| **A — 구현** | `backend/`·`frontend/` 코드를 고쳤다 | 스펙의 「구현 순서」를 갱신한다 | 완료면 `구현완료`로, 아니면 `구현중`으로 |
| **A — 설계** | `docs/specs/`만 고쳤다 | 건드리지 않는다 | 승인되면 `승인`, 아니면 `초안` 유지 |
| **B/C** | 목업 대조 수정 / 버그 수정 | 해당 없음 (스펙 없음) | 해당 없음 |

`git diff --stat main...HEAD`로 확인하라.

## 1단계: 검증 실행

```bash
[ -f backend/gradlew ] && (cd backend && ./gradlew clean check)
[ -f frontend/package.json ] && (cd frontend && pnpm typecheck && pnpm lint && pnpm test && pnpm build)
./scripts/check-spec-coverage.sh
```

**출력을 실제로 확인하라.** 실패가 있으면 다음 단계로 가기 전에 사람에게 알리고, 고칠지 이
상태로 넘길지 확인받는다.

설계 세션이라면 코드 검증은 해당 없고 `check-spec-coverage.sh`만 돌리면 된다. 스펙을 새로
썼다면 `status: 초안`이라 건너뛰는 게 정상이다.

## 2단계: 스펙 체크박스·status 갱신 (A만)

`docs/specs/`의 해당 스펙에서 **이번 세션에 실제로 완료한 「구현 순서」 태스크**만
`- [ ]` → `- [x]`로 바꾼다.

- **중간에 멈췄으면 거기까지만 체크한다.** 앞당겨 채우지 않는다
- 모든 태스크가 끝나고 검증이 초록이면 `status: 구현완료`로 바꾸고 **「구현 순서」 절 자체를
  지운다**(`docs/conventions/workflow.md`「문서 수명」) — 태스크는 이제 git 히스토리가 기억한다
- **설계 세션은 체크박스를 건드리지 않는다.** 시나리오·AC·계약 본문만 고친다

## 3단계: 스펙과 실제가 어긋났는지 확인

구현하면서 스펙(특히 「구현 순서」)이 틀렸다는 게 드러났다면 **지금 스펙을 고친다.**

**AC를 바꿔야 하는 상황이면 고치지 말고 사람에게 보고하라.** AC는 승인된 계약이다.

## 4단계: `docs/GOTCHAS.md` 갱신

**다음에 또 걸릴 만한 함정**을 이번 세션에서 발견했다면 추가하라(≤100줄, 넘으면 가장 오래되고
덜 중요한 항목을 정리한다). 반대로 이번 세션에서 그 함정의 원인을 없앴다면(코드를 고쳐서 더는
재발하지 않는다면) 해당 항목을 지운다.

**한 세션의 이야기(막힌 지점, 이번에만 있었던 실수)는 여기 쓰지 않는다.** 그건 5단계의 PR
본문으로 간다. GOTCHAS는 "다음 세션도 또 만날 것"만 남긴다.

## 5단계: 커밋 + 푸시

`docs/conventions/git.md`의 Conventional Commits를 따른다.

```bash
git add -A
git commit -m "<type>(<scope>): <제목>

<본문 — 무엇이 아니라 왜>

Co-Authored-By: Claude <noreply@anthropic.com>"
git push -u origin <브랜치명>
```

**테스트가 빨간 채로 끝나면 제목 앞에 `WIP:`를 붙인다.**

## 6단계: PR 생성/갱신 + 이슈 정리

### PR이 없다면 (태스크를 완료한 경우에만 생성)

```bash
gh pr create --fill-first --body "$(cat <<'EOF'
## 무엇을
<한두 문장>

## 왜
관련: docs/specs/<스펙>.md
Closes #<관련 이슈가 있으면>

## 구현 중 결정
<사람에게 묻지 않고 정한 것과 이유. 없으면 "없음">

## 어떻게 확인했나
- [x] `cd backend && ./gradlew clean check` 통과
- [x] `./scripts/check-spec-coverage.sh` 통과
- [x] <수동 확인 항목>

## 남은 것
<없으면 "없음">

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

**태스크가 미완이면 PR을 만들지 않는다.** 브랜치만 푸시해두면 다음 세션이 이어받는다. 막혀서
끝난 거라면 draft PR을 열어 본문에 무엇에 막혔는지 적는다.

### PR이 이미 있다면

`gh pr edit <번호> --body "..."`로 「구현 중 결정」·「어떻게 확인했나」·「남은 것」을 갱신하라.

### 이슈 정리

이번 세션이 처리한 이슈가 있으면 `gh issue close <번호> --comment "..."` 하거나, PR 본문의
`Closes #N`이 머지 시 자동으로 닫게 둔다. 새로 발견했지만 지금 하지 않는 할 일이 있으면
`gh issue create`로 남긴다(라벨: `lane:A`/`lane:B`/`lane:C`).

## 7단계: 마무리 보고

사람에게 3~5줄로 보고하라:

- 무엇을 끝냈고 어디까지 갔는지
- 검증 결과 (초록/빨강, 빨강이면 무엇이 왜)
- 다음 세션이 할 일
- PR 링크 (있으면)
